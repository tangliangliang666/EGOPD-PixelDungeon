## 6. 常见陷阱速查

| 现象 | 原因 | 处理 |
|---|---|---|
| 窗口内暂存物品（已 detach 出背包）切后台/场景重建后丢失（移动端创作/强化/分解/附魔窗口的 bug） | 物品只存在于 UI 字段（已从背包 detach、不可序列化）；`GameScene.onPause()` → `saveAll()` 先于任何退回执行，进程被杀后读档即丢；旋转/尺寸变化重建场景时窗口直接 destroy 也不退 | 持有物品的窗口实现 `windows/WindowReturnsItems`：`destroy()` 覆写先 `returnAllItems()`（兜底一切销毁路径），并提供 `returnItemsAndClose()`；`GameScene.onPause()` 保存前对场景内所有 `WindowReturnsItems` 统一收尾（创作/强化/分解/附魔四窗已接；参考 AlchemyScene.clearSlots 范式） |
| 指令每回合 *哔哔* | 旧档缺失 `speedMultiplier` 键 → getFloat 返回 0 | 读档钳制默认值 + `act()` 防御 `turnsLeft<=0→1` |
| 图标全部错位 | TX_HEIGHT 与 items.png 实际高度不符 | 同步高度（现 800） |
| 天赋图标错 1 格 | 枚举索引与图内绘制位置不一致 | 核对 Talent 枚举 icon 值 |
| 指令终端被换下/嬗变 | 未设 unique / 未拦 doUnequip | `unique=true` + `doUnequip` 返回 false + KindofMisc 禁用选项 |
| 自定义神器"想出售 / 想被嬗变却被挡"，或顺手删 `unique` 后变成可被偷、可被拟态吃掉 | `unique` 在本作**一标三用**：①`Shopkeeper.canSell` 禁售（`unique && !stackable`）；②`ScrollOfTransmutation.usableOnItem` 用 `return !item.unique` 禁嬗变；③`Thief` / `CrystalMimic.steal` 用 `!unique` 判"可偷/可吃"（另被 `DriedRose` 幽灵窗口用来拒收） | 要**单独**放开某一项就覆写对应谓词——出售 `Item.sellable()`（默认「非 unique，或可堆叠」）、嬗变 `Item.transmutable()`（默认 `!unique`）；`canSell` / `usableOnItem` 已改为调它们。**别直接删 `unique`**，否则神器会被嬗变卷轴重掷、被水晶拟态永久吃掉。被嬗变掉后需要收尾的（爱慕 → 溶解之爱反叛倒计时）覆写 `Item.onTransmuted(Hero)`，回调点在 `ScrollOfTransmutation.onItemSelected` 的替换动作之前。参考 `TearSwordBlessing`（**已去掉 `unique`**，sellable / transmutable 虽仍显式覆写为 true，但可售/可嬗变已由默认实现给出；代价是它也变回「可被偷 / 可被拟态吃」的普通战利品，只有 `level() >= 1` 之后才免疫）/ `Admiration`（本就没有 unique）；仍标 `unique` 的 `RevengeLedger` 连出售也做不了（且它的 `value()` 本来就是 0） |
| FlavourBuff 秒消失 | `Buff.affect` 无时长 | 用 `Buff.affect(..., 99999f)` 或 `Buff.prolong` |
| 「获得 buff 时」的副作用（提示语 / 音效 / 一次性特效）跑到 buff 快要结束时才触发 | **`FlavourBuff.act()` 语义是「wait and detach after a time」，整个生命周期只被调用一次（不是每回合一次）** ⇒ 写进 `act()` 等于在到期那一刻才跑。2026-09-18 实测：预知眼过热语音挂在 `OdinsEyeOverheat.act()` 里，结果在第 30 回合、过热即将结束时才响 | 「获得时」的副作用写在**授予处**（`Buff.affect` 的调用方，与获得时的浮字/特效并排——`OdinsEye.overheatPenalty()` 就是范例）；`act()` 只适合写「结束时」的收尾。覆写 `attachTo` 也可在获得时触发，但**读档重建同样走 `attachTo`**（反序列化已调 `restoreFromBundle`，之后才 `attachTo`）⇒ 会造成重复触发 |
| 手动攻击不随机形态 | 双蛇杖形态在 `accuracyFactor` 才 roll | 显式调用 `rollFormForAttack()` / `forceScytheForm()` |
| 新武器打不出 | 未加入 Generator 掉落池 | 调试窗生成；入池需改 Generator 列表 |
| 消息文本显示 "%1$d" 字面量 | 模板里单写 `%`（如 "20%"）被 `String.format` 当格式符 → IllegalFormatException → 返回原文 | **带参数的模板中字面百分号必须写 `%%`**（"20%%"）；无参调用不触发 format 可不用转义 |
| 命中时目标特效不显示 | 从**攻击者**代码（武器 proc / Hero.attackProc）跨单位对目标发射粒子 | 受击特效必须在**目标自身的 `defenseProc`** 里触发（参考酸性史莱姆酸液/水晶守卫格挡）；可用"装备时 buff + 常驻发射器"临时验证特效本身 |
| 多段伤害击杀 BOSS 后出口不解锁 | 光环/附带伤害对**已死的目标继续调用 damage()** → 走 `Goo.damage()` 覆写 → `if (!BossHealthBar.isAssigned())`（boss 已死 isAlive=false）→ **重新 assignBoss + seal() 把层又锁上**（日志表现为 unseal 后紧跟一次 seal）。覆写的守卫都在 `super.damage()` 里，**来得太晚** | **判定必须做在调用方**：① 打之前先判一次 `目标.isAlive()`（目标可能已被同一次攻击的**主伤害**打死——如 `TearSword.strikeAt` 在 `Hero.onAttackComplete` 的 `attack()` 之后结算附加伤害）；② 多段则**每段之后各判一次**，死亡立即停止后续段（薄暝 proc/光环四连击即此修复）。`Char.damage()` 自带的 `!isAlive()` 守卫**拦不住 boss 覆写**（覆写不判死亡就先 assignBoss+seal）。兜底：`Mob.die()` 归属块前对 BOSS 无条件 `unseal()`（幂等）；全工程实测 **30 个** `actors/mobs` 类覆写了 `damage()` 且整个覆写体内不出现 `isAlive()`（含 Goo/Tengu/DM300/DwarfKing/YogDzewa/CrystalSpire/Masterpiece/RingfingerAutomaton 等 boss，也含 Mob 基类与 NPC），新增任何「附加伤害」都要按此判定 |
| 法杖默认不能对自己施法 | `Wand.zapper` 拦截 `target == curUser.pos`（提示 self_target），只有"储能护盾"天赋分支放行 | 自定义 `CellSelector.Listener`：显式判断 `target == curUser.pos` 直接走自身效果分支（不走 Ballistica 弹道），参考法师储能护盾写法 |
| 特效显示在怪物贴图之下被遮挡 | 特效挂到 `ch.sprite.parent`（mobs 组内，与角色同级/之下） | 挂到 `GameScene.effect(...)`（effects 层，在 mobs 之后 add → 渲染在角色**之上**）；要渲染在角色**之下**则挂 `GameScene.floorEmittersAdd(...)`（floorEmitters 层，在 mobs 之前 add） |
| 远程施法（直接 `ch.damage()`）命中无受击特效 | 直接结算伤害不经过 `defenseProc`（只有近战攻击链走） | 施法/直伤代码里**显式调用特效**（damage 前播放，避免目标死亡后精灵不可用） |
| buff 想显示跟随单位的贴图标记 | — | 参考 `TargetMarker`（`ItemSprite` 子类 + `update()` 里每帧 `place()` 同步到 `target.sprite.center()`，目标不可见则隐藏）；由 buff 的 `fx(boolean)` 挂载/销毁，`Char.updateSpriteState()` 读档时自动重建（`marker == null` 防重复） |
| 站立不动时 buff 粒子消失 | buff 在 `act()` 里每**回合**（游戏时间）burst，不行动时游戏时间不走 | 改为 buff 持有**常驻发射器**（`target.sprite.emitter().pour(...)`，按真实时间持续喷发），attach 启动、detach 销毁 |
| `:desktop:release` 报 "Failed to clean up stale outputs" | 游戏进程正在运行，锁住桌面构建产物 | 先关闭游戏（检查进程命令行含 "My Pixel Dungeon"）再构建 |
| 游戏静默退出：无窗口、零输出、exit code **268435466**(0x1000000A)，但 `:desktop:debug` 显示 BUILD SUCCESSFUL | Gradle 守护进程是在受限环境（如 TRAE 沙箱）中启动的，游戏 JVM 作为其子进程继承了 Job Object 限制，启动早期即被终止 | `gradle --stop` 停掉全部守护进程，用干净（无沙箱）终端重新构建启动；AI 代理提权/变更权限后必须先 stop 旧 daemon |
| `:desktop:debug` 崩溃但仍显示 BUILD SUCCESSFUL | debug 任务配了 `ignoreExitValue = true`，掩盖游戏进程崩溃 | desktop/build.gradle 的 debug 任务 doLast 里已打印 `game process exit code`（勿删）；退出码 0=正常退出，1=崩溃弹窗后退出，其他值看第 6 节首行 |
| 编辑某个 `.java` 后编译报 `unmappable character` / 中文注释变乱码 | 写入端编码错乱，**同一文件里两种编码混存**（2026-09-17 在 `ClassArmor.java` 一次踩中两种）：① 新写入的中文注释**整行按 GBK 落盘**；② **行尾 3 字节汉字的最后一字节被 clobber 成 `?`**（`衣`=`E8 A1 A3` ⇒ 残留 `E8 A1 3F`，`套`=`E5 A5 97` ⇒ `E5 A5 3F`）。两类都会让文件不再是合法 UTF-8，而 `core/build.gradle` 指定 `options.encoding='UTF-8'` ⇒ **直接编译失败**（且损坏可能出现在**离改动很远**的行上，别只看改动点） | **改完任何 `.java`/`.properties` 立刻跑 `python _chk/check_utf8_all.py`**：全仓扫，任一文件非 UTF-8 即 FAIL，并另报「汉字后紧跟 `?`」的可疑行（合法 UTF-8 时的残留特征）。修复样板 `_chk/fix_classarmor_encoding.py`：按 `utf-8 + surrogateescape` **无损**读入 → 只替换出事的那几行（唯一性断言 + 逐行打印新旧）→ 写回后再断言「可完整解码 / 无代理字符 / 关键内容在」。**不要**再用「整文件按 GBK 解码再写 UTF-8」的老办法——混存文件会报错或二次污染 |
| 新写的文本被莫名其妙划掉 / 显示成删除线 | 文本里出现了 `~~`（`RenderedTextBlock` 的删除线开关标记） | 要**显示**字面 `~` 时用单 `~`（如"看得清清楚楚哦~"）；只有成对的 `~~` 才触发删除线 |
| 新增房间后**永远刷不出来**，或某个老房间概率明显异常，且**编译与运行都不报错** | `StandardRoom.chances` 是 `float[27][]`，**每一行的长度都必须等于 `rooms.size()`**（当前 34）。往 `rooms` 加了新房间却漏给某个 `chances[depth]` 追加权重 ⇒ 该深度数组比 `rooms` 短，`createRoom` 里按下标取权重时相对错位；多一个则越界 | 加房间后**逐个数一遍 27 行的长度**（`rooms` 加一项 ⇒ 所有 `chances[d]` 都要各加一项）。用编辑器生成的房间请照 `docs/terrain-editor-guide.md` §5.3 的四步清单走 |
| 手写的房间地形**和预览图对不上 / 外圈漏风 / 门不生效** | ①`Room.right` / `bottom` 是**闭区间**（继承自 `Rect`），宽度 = `right-left+1`，按半开区间算会整体差一格；②门必须落在**外圈**上（`placeDoors` 只在外圈找门位），开在内圈的门不会产生关卡连接；③`StandardRoom.paint` 没有基类实现，每个子类都要自己写 `Painter.fill(level,this,WALL)` + `fill(level,this,1,EMPTY)` 这两步骨架 | 用 `tools/terrain-editor/index.html` 画（画布会即时标出「门不在外圈」和「外圈破损」，生成的代码坐标已按相对偏移直译）；手写时照抄上游任一 `StandardRoom` 子类的骨架两步 |
| **房间放了陷阱却看不见 / 踩不到**，而 `map[]` 里明明是 `Terrain.TRAP` | **陷阱不是地形。** `Terrain.TRAP` 只是"这格下面有个陷阱"的占位符；真正让陷阱存在的是 `Level.traps` 这个 `SparseArray<Trap>`（与 `map[]` **平行**的另一套）。`TerrainFeaturesTilemap.getTileVisual(pos,tile,flat)` 的判断顺序是 ① `traps.get(pos)` 命中 ⇒ `(trap.visible ? (trap.active ? trap.color : Trap.BLACK) + trap.shape*16 : -1)`；② `plants.get(pos)` ⇒ `plant.image + 7*16`；③ 才轮到 `GRASS`/`HIGH_GRASS`/`FURROWED_GRASS`/`EMBERS`。只写地形 ⇒ 什么都不画 | 必须调 **`level.setTrap( new XxxTrap(), pos )`**（内部已做 `traps.put` + `GameScene.updateMap`，**不需要**再 `Painter.set`）。植物是 **`level.plant( new Xxx.Seed(), pos )`** —— 入参是 `Plant.Seed` 而不是 `Plant`（上游 13 种植物都带同名内部 `Seed` 类；写成 `new Sungrass()` 会编译错 `不兼容的类型: Sungrass无法转换为Seed`）。帧号：陷阱 `color + shape*16`（`RED=0…BLACK=8` × `DOTS=0…LARGE_DOT=6`），植物 `image + 7*16`。用编辑器摆（`tools/terrain-editor/index.html` 的「覆盖层」面板，生成代码已含正确的 `setTrap`/`plant` 语句）；核验 `_chk/verify_trap_tables.py` + `_chk/verify_codegen_compiles.js`（真 javac 编译） |
| **想在某格放道具**，用了 `level.addItemToSpawn(item)` 结果**位置随机**（且编译完全能过） | `addItemToSpawn(Item)` 只把物品推进 `itemsToSpawn` 队列，随后 `RegularLevel.createItems()` 通过 **`randomDropCell()`** 消费 ⇒ 落点随机。它**不是**定点投放入口 —— 而且字符串/编译层面都看不出错 | 定点投放**唯一**入口是 **`Level.drop( Item, int cell )`**（字节码 `Level.drop:(L…items/Item;I)L…items/Heap;`，返回 `Heap` ⇒ 可链式 `level.drop(...).type = Heap.Type.CHEST`）。物品在 `Level.heaps`（`SparseArray<Heap>`），`Heap` 自带 `ItemSprite` 挂 `GameScene` 的 objects 组 ⇒ **地图格仍是普通地板，不要改地形**（这点与陷阱相反）。`Room.paint()` 里 `drop` 有上游先例（`RingRoom.placeCenterDetail` / `MassGraveRoom` / `RatChestChasmRoom` / `RatKingRoom`）。核验 `_chk/verify_item_tables.py` + `_chk/verify_codegen_compiles.js`（反汇编断言 `Level.drop(Item,int)→Heap` + `putfield Heap.type`） |
| **物品图标从图集里取，帧号算出来是空帧 / 画成了别的物品** | `ItemSpriteSheet` 的坐标是 **0-based**：`xy(x,y){x-=1;y-=1;return x+WIDTH*y;}`、`WIDTH=TX_WIDTH/SIZE=256/16=16`。按 `(col-1)*16` 手算会得到「空帧」的**假结论**。更坑的是 **`Sheet.prototype.draw()` 对任何合法索引都返回 `true`**（哪怕整帧全透明）⇒ `if (!drew)` **不是**空帧判据 | 用 **`solidCount(idx) > 0`** 判真实帧。口粮占位帧 = `FOOD=xy(1,28)=432`、**`RATION=FOOD+5=437`**（col 5 / row 27 / 像素 `(80,432)`，实测 164 个不透明像素）。`items.png` 在 `core/src/main/assets/sprites/`（**不在** `environment/`），与地形图集是**两张图**。真名是 **`Food`**（`items/food/Food.java`，`image = ItemSpriteSheet.RATION`）—— 不存在叫 `Ration` 的类。核验 `_chk/verify_item_placeholder.py`（公式/真像素/drawImage 三层证明） |
| **首帧渲染崩了 ⇒ 整个界面空白**（下拉框全空、画布 16×16、代码框空），报 `Cannot read properties of null (reading 'draw')` | 初始化是**同步**的、而资源是**异步**加载的：`boot()` 同步跑到底 → `fullRefresh() → draw() → render()`；图集却是 `new Image(); im.onload = ...`。⇒ **首帧必定早于 `setSheets()`**。加新图集（例如把 `items.png` 内联进 `assets.js`，216KB → 332KB）改变时序就会让它必炸 —— 在此之前只是"加载够快所以没炸" | 在渲染入口做**空值保护**：`render()` 里 `ctx.scale` 之后直接 `if (!S.sheet) return;`（其它图集如 `S.features` 同样加 `&& S.features`）。**别用 `setTimeout`/轮询兜** —— 那只是把竞态藏起来。核验侧要相应显式 `setSheets(...)`。**通用教训：任何"资源加载完后画面才对"的实现都是脆的，首帧必须能在资源缺失时安全返回** |
| **把「让页面能用」的初始化放进 IndexedDB 回调 ⇒ 页面永远起不来**（画布 0×0，**控制台一声不响**） | `file://` 是 opaque origin，Edge 的 `indexedDB.open()` 可能**既不触发 `onsuccess` 也不触发 `onerror`** ⇒ 回调永挂。凡把收尾/刷新挂在它后面的，全部不执行。改用「先同步、后异步补充」结构即可根治 | ①同步做完必需初始化（建下拉、铺画布、刷代码），②异步存储只做**追加式**补充，且**回调必须"至多执行一次"**（`setTimeout` 强制放行 + `done` 闩），③`openDB` 另加超时与 `onblocked`。**通用教训：可用性初始化绝不能依赖异步存储回调**。核验 `_chk/verify_atlas_import.js`（59 项，含"模拟刷新后恢复"）|
