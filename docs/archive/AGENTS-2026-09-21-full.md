# AGENTS.md — 开发经验手册（通用）

本文档为**通用开发经验手册**：适用于任何自定义职业/功能开发（构建流程、文本本地化、贴图规范、SPD 框架机制、通用陷阱、通用物品/特效经验）。各职业与功能的**具体实现细节**已按类归档，见第 5 节内容地图。

> **同步约定**：通用机制/规范/陷阱的新发现记入本文档（变更类经验记入第 6 节陷阱速查表）；职业与功能专属的新开发/变更/踩坑记入对应档案文件（docs/ring-master.md、docs/oracle-class-design.md、docs/features.md）。文档中"现为 XXX"字样均为最新状态，以对应文件为准。

## 1. 构建与运行（快速参考）

```bat
rem 编译核心模块（最快反馈，桌面调试前必跑）
set JAVA_HOME=D:\PD\tools\jdk-21.0.12.1+1
set GRADLE_USER_HOME=D:\PD\.gradle
D:\PD\tools\gradle-9.4.0\bin\gradle.bat :core:compileJava --console=plain
```

- **退出码 1 但输出 `BUILD SUCCESSFUL` = 正常**（javac 的 stderr 警告）。真正的失败会输出 `错误:` / `error:` 行。
- **AI 代理工作流**：编译成功后**不要自行启动游戏**——游戏窗口无输出可采集，游戏内内容只能人工验证；直接告知用户进行测试即可。
  - **源码级核验用单文件 javac**（不代跑 Gradle，流水线见 skill `egopd-source-verify`）。一个必踩的坑：
    classpath **必须带上 `D:/PD/services/build/classes/java/main`**。`NewsService` / `AvailableUpdateData`
    在**独立的 `services` 模块**里，漏了它会甩出 19 个「找不到符号 / 程序包 NewsService 不存在」的
    **虚假错误**，全落在 `scenes/TitleScene.java`、`services/news/News.java`、`scenes/NewsScene.java` ——
    与本次改动毫无关系，极易误判成「改坏了」。（2026-09-20）
- 桌面运行：`build-desktop.bat`（F2 打开 WndDebug 调试窗：药水/卷轴/武器/远程/防具/神器/杂项/Buff/怪物标签页，点击即生成/施加；「杂项」标签浅层扫描 items 根包，含天狗面具、矮人王冠、护身符、复活十字架等关键物品）。完整输出写入 `d:\PD\desktop-debug.log`，启动前自带数据目录写入自检。**报"游戏打不开"先查第 6 节"游戏静默退出"条目（通常是 Gradle 守护进程被沙箱污染，`gradle --stop` 后重试）**。
- **Android APK**：SDK 已装在 `D:\PD\tools\android-sdk`（`local.properties` 已指向）。构建：
  `gradle.bat :android:assembleDebug` → 产物 `android\build\outputs\apk\debug\android-debug.apk`（debug 签名，可直接安装；`assembleRelease` 未配置签名）。
  - 环境变量与 `build-desktop.bat` 一致：`JAVA_HOME=D:\PD\tools\jdk-21.0.12.1+1`、`GRADLE_USER_HOME=D:\PD\.gradle`。
  - **版本号**：`build.gradle` 的 `ext.appVersionCode / appVersionName`（2026-09-20 现为 931 / `0.3.1`）。编码约定
    **`900 + minor*10 + patch`**（0.2.5⇒925、0.3.0⇒930、0.3.1⇒931）；打包后 `output-metadata.json` 与 `aapt dump badging` 均可核对
    实际写入值（debug 变体 `versionName` 会加 `-INDEV` 后缀、`applicationId` 加 `.indev` 后缀）。
  - **出 EGOPD 新版本的固定三步**（2026-09-18 起）：① 根 `build.gradle` 改 `appVersionCode/appVersionName`；
    ② 在 **`ui/changelist/EGOPD_Changes.java`** 追加 `new ChangeInfo("EGOPD vX.Y.Z", true, "")` 并把该版本的改动逐条
    `changes.addButton(...)`（**这是 EGOPD 改动历程唯一该写的地方**）；③ `:android:assembleDebug` 后拷成
    `EGOPD_<版本名>.APK`。改动栏界面的页签在 `scenes/ChangesScene.java`：`EGOPD_TAB = 0` 是 EGOPD 页且**默认选中**，
    版本页顺延为 case 1~8；该页**不显示**上游那句「改动详情仅提供英文版本」（`lang_warn` 已按页签排除）。
    页签按钮 9 个分两行排（上游 8 个正好占满一行，故 `ph` 由 `h-36` 改为 `h-55` 让出 19px）。
  - **归档约定**：构建完把 `android-debug.apk` 复制为 `EGOPD_<版本名>.APK`（同目录）。注意 `packageDebug` 会**先清空
    output dir**，上一版的 `EGOPD_x.y.z.APK` 会被自动删掉，所以若要留旧版请先拷出。
  - **只改源码/文本后直接重新 `:android:assembleDebug` 即可**（增量，约 35s；`:core:compileJava` 会连带重编）。
  - 用户级约定：`assembleDebug` 允许 AI 执行（打包验证），但 `：core:compileJava` 等编译任务默认由用户自己跑。
  - **打包前先确认没有别的构建在跑**：桌面调试（`:desktop:debug`）会长时间持有 `.gradle\9.4.0\executionHistory\executionHistory.lock`，
    此时其它构建一律以 `executionHistory.lock (拒绝访问。)` 失败（哪怕加了 `--no-daemon`）。正确做法是等游戏退出/桌面构建结束再打包；
    **不要**用 `--project-cache-dir` 另开缓存来绕锁 —— 两个构建会互踩 `android\build\intermediates`，表现为 dexBuilder 写
    `desugar_graph\...\graph.bin (拒绝访问。)`。
  - **中断构建后的恢复三步**（杀掉客户端**不会**终止 Gradle 守护进程，它会继续跑并占住中间产物）：
    ① `gradle.bat --stop`；② 若它报 "No Gradle daemons are running" 却仍有 ~1GB 的 `java.exe`（命令行含 `GradleDaemon`）→ 直接结束该 PID；
    ③ 删 `android\build\intermediates\desugar_graph`（随后 dexBuilder 回退非增量并打印 "Fall back to non-incremental mode"，属正常，构建仍 SUCCESSFUL）。
  - **打包核验链**（本次已用）：`output-metadata.json` / `aapt dump badging` 看版本 → 确认日志里 `:android:dexBuilderDebug` 是 executed（非 UP-TO-DATE）
    → `javap -c Generator$Category.class` 确认新类字面量在数组里 → `unzip` 出 jar 内 class 与 `build/classes` 上的 md5 一致，
    证明 APK 真的含本次改动。
  - **名字/图标打包后必查**：`aapt dump badging android-debug.apk | grep -E "^package|application-label:|application-icon-480"`。
    `application-label:` 应等于 `appName`；`application-icon-*` 全部指向 `res/mipmap-anydpi-v26/ic_launcher.xml`（自适应图标，
    ⇒ 只改 `mipmap-*/ic_launcher.png` 那套扁平图真机看不到）。核对 APK 内图标是否真等于工程源文件，用 Python `zipfile` 取
    `res/mipmap*` 逐张比 md5（`res/mipmap-anydpi-v26/ic_launcher.xml` 会被 aapt2 编成**二进制 XML**，md5 必然不同，属正常）。
  - **体积变化要能解释**：`:android:assembleDebug` 产物含 `core/src/main/assets` 全部内容，所以**新增素材（音效/音乐/图集）会撑大 APK**。
    排查用「按顶层目录统计条目数与体积」对比上一版（0.2.5 由 37.5MB→50.2MB 就是新增 49 个 mp3/png 素材所致，与图标无关——图标只增约 5KB）。
  - **⚠️ 比体积前先看有没有「空洞」**（2026-09-18 踩坑）：ZipFlinger 的**增量打包**会把变小的条目原地重写，旧的更长数据留在原位成为
    垃圾空洞。实测 `EGOPD_0.2.5.APK` 有 **259 处共 898,040 字节空洞**（最大一处 293KB 在 `classes3.dex` 前），而重打一遍的 0.3.0 只剩
    502 字节（仅 PNG 的 3 字节对齐缝）⇒ **同样的 533 条 assets、压缩总量只差 223 字节，文件却小了 897KB**。
    判定「内容到底变没变」不要用文件大小，用下面的**全量资产比对**。
  - **全量资产比对（最硬的证据，2026-09-18 新增）**：用 Python `zipfile` 把 APK 内每个 `assets/*` 条目 md5 与工作区
    `core/src/main/assets/<相对路径>` 逐条比 ⇒ 能一次性回答「我改的素材到底进包没有」。本次结果 **533/533 全部逐字节一致**。
    注意 `zipfile` 对**非 UTF-8 标记**的中文名条目按 cp437 解码，要 `name.encode('cp437').decode('utf-8')` 还原后再拼路径，
    否则会误报「无源文件」。顺带一查：`assets/` 里混着 `.aseprite` 工程文件与中文名工作图（`精灵-0001.png` 等
    **9 个、1.14MB**），它们同样会被打进 APK —— 清素材时留意。
  - **新类是否真进包**：`python -c "z=zipfile.ZipFile('android-debug.apk'); dex=b''.join(z.read(n) for n in z.namelist() if n.endswith('.dex')); print(dex.count(b'EGOPD_Changes'))"`
    —— dex 里能搜到类名与新增的中文字面量即证明编译产物已进包（本次 `EGOPD_Changes` 命中 3 次、`EGOPD v0.3.0` 与中文提示各 1 次）。
- 只改文本（messages 属性文件）时无需动代码，重新打包即生效。

## 2. 文本与本地化

- **大多数文本**在 `core/src/main/assets/messages/*_zh.properties`（`actors` 怪物/buff/天赋/技能、`items` 物品、`windows` 窗口、`journal` 日志、`levels` 楼层、`misc` 杂项）。格式：`键=值`；`_xxx_` 强调色；`\n` 换行；`%s`/`%1$d` 是占位符**不可删**。
- **行内标记（`ui/RenderedTextBlock`）**：`_文字_` 或 `**文字**` = 强调色；`~~文字~~` = **删除线**（2026-09-13 新增，标记自身不渲染）。三者在**任何** `RenderedTextBlock` 文本里都生效——包括 `StyledButton` 文字、`IconTitle` 标签、`WndHeroInfo` 标题、存档槽名字、任务日志面板。删除线是**画上去的**（白色 `ColorBlock` + `hardlight`，在 `layout()` 末尾贴到词中点），因为 `pixel_font.ttf`/`droid_sans.ttf` 都**没有** U+0336 之类的组合删除线字形。**注意**：`GLog` 的青色前缀常量就是 `"~~ "`，但 `ui/GameLog` 会先 `substring` 剥掉，不会串进来；新写文本时别让正文以裸 `~~` 开头。
- **自定义职业/物品常大量使用硬编码中文**（不走 messages），改文本需改代码；各职业的硬编码文本位置清单见对应档案：神谕→docs/oracle-implementation.md、环指→docs/ring-master.md。
- `Messages.get(Class, key)` 会沿**父类链**查找键：子类未定义 `desc` 等键时继承父类文本（新武器复制短剑文本即靠此机制）。
- **「列表类」技能文本必须自带技能名**（2026-09-17，「中指长兄」三技能）：原版 `short_desc` 习惯把名字写进句子里（「战士_苦痛坚忍_，跳过…」），本 mod 的多个技能却直接从描述起笔 ⇒ `WndChooseAbility`（选择盔甲技能界面）、`WndHeroInfo` 技能页、`ClassArmor.desc()` 三处列表里只剩一串话、**认不出是哪一门技能**。现统一走 `ArmorAbility.namedShortDesc()`：**描述已含名字（不区分大小写）就原样返回**（原版技能不重复），**否则在开头补一行 `_技能名_` + `\n`**；三个消费点已全部改用它，新增技能不必各自拼名字。英文侧尤其要按「不分大小写」判：原版把名字写成句内变形（`endure` → `_Endures_`），逐字比较会漏判成「需要补名字」。预演/回归：`_chk/check_named_short_desc.py`（模拟 `titleCase` + 大小写不敏感匹配，逐技能打印列表里实际会显示的文本并断言中指三技能都补上）。
- 上述列表用的是 `RedButton`（`StyledButton`）+ `RenderedTextBlock`，两者都支持 `\n` 硬换行与 `_强调_`；`WndChooseAbility` 的按钮高度靠「先 `setSize` 触发一次布局 → 再 `reqHeight()` 取换行后真实高度」这套写法（同 `WndMonkAbilities`），所以**给按钮文字加换行不会溢出**。
- **数值类信息只写在「描述文本」里，即时消息（`GLog`）不写具体数字**（2026-09-16 用户约定）：门槛、消耗、百分比这类需要玩家**事先权衡**的信息写在物品/天赋/技能的 `info()` / `desc()`（`Messages.get(..., "desc")`）里；`GLog.i/w/p` 的即时报文只给感受性措辞（如「账簿上的仇怨还太淡，尚不足以燃起」），不写「需要 20%」。好处：战斗中不弹一堆数字，且改数值时不必逐条同步文案（`GLog` 那侧不带参 ⇒ 也不会踩格式化坑）。参考 `RevengeLedger`（`no_charge` 不带参、`desc` 写明 20%/2%）。
- **改一个机制的「行为」时，先 `grep` 全部提及它的描述键**——同一套机制通常在 **3~4 个键**里各写了一遍（招式自己的 `desc` ×2 语言、所属天赋的 `desc` ×2、职业/转职的长描述 ×2）。本作实测（2026-09-16「踏碎改成单体」）：只改 `move.stomp.desc` 会漏掉 `herosubclass.loyal_pilgrim_desc` 里的同一句话。**做法**：用机制的中文关键词（如「周围八格」「英勇之跃」）在 `core/src/main/assets/messages/` 下 `grep`，再按 `*-zh`/base 两两成对改。
- **描述文本只做功能描述，不写修饰句**（2026-09-16 用户约定，当晚已按此回改过一轮）：天赋 / 物品 / 转职的 `desc` **直接从 `_+1：_` 或效果本身起笔**，不要加开场白式的文学化铺垫（英文侧实测删掉了 `Wielding a blade well is a matter of familiarity, not of force.` / `Whatever stands in Laevateinn's way ends up as a puddle.` / `Every layer of the seal that comes off leaves the blade a little keener.` 三句）；`actors.buffs.*` 的 `desc` 同样直接写数值效果，不写「这个单位正在……化开」这类叙述。**层级标签统一 `_+1：_`（zh）/ `_+1:_`（en）——首档也要带下划线**，只写 `+1：` 会和后两档样式不一致。**英文侧要跟中文同步**：中文删了铺垫而英文留着的，属于未对齐（本作长期以 zh 为准，回改时一并处理）。
- **换行只认反斜杠 `n`**：`\n\n` 误写成 `/n/n`（正斜杠）**不会换行也不报错**，只会在面板里原样显示 `:/n/n_+1:_`。批量核验：`grep -c "/n/" core/src/main/assets/messages/ -r` 应为 0（2026-09-16 在 `actors.properties` 一次揪出 9 处，全在手掌/前二老板的 T3 天赋里）。
- **用脚本批量写 `*.properties` 时，落盘前必须把真换行转成字面量 `\n`**（2026-09-17 踩坑，「即刻处刑[莱瓦汀]」）：Python 源码里写 `'…。\n\n下一段…'` 会被解释成**真换行**，写进文件后一条 entry 断成多行——续行没有 `=`，会被解析成一堆垃圾键（表现是「文本只剩第一段」，而**加载不报任何错**）。做法：块里照常写真换行（好读），落盘前统一 `line.replace('\n', '\\n')`，并自检「有没有缺少 `=` 的非空非注释行」。核验脚本两条：`_chk/fix_newline_escape.py`（接回断行 + 期望值逐键断言）、`_chk/InstExecLocCheck.java`（真 `Properties.load` + 按真实实参类型 `String.format`，并断言**每个实参都出现在结果里** ⇒ 能抓出「值被截断成只剩第一段」）。

## 3. 贴图与图标

- **items.png 现为 256×800（50 行）**（2026-09-12 由 640 扩到 800，行 41-50 为最新扩展预留区，除 41行1列外空白；行 36-40 为自定义内容区：36行1/2=割腕/悔恨、37-40行=人体派作品武器图标，**39行7/8列=泪锋的加护两形态**，其余空白）：`ItemSpriteSheet.TX_HEIGHT` 必须等于实际高度，否则全物品图标错位（曾因 528→544、576→640、640→800 未及时同步而出过全局错乱）。PNG 高度可从 IHDR 读取（**大端**，PowerShell 读 Int32 需反转字节，宽=偏移16-19、高=偏移20-23）。
- `xy(列, 行)` 是 **1 基**（**第一参=列、第二参=行**，内部 `x-=1; y-=1`），每行 16 格（WIDTH=16）。例：GLOWING_PEBBLE=xy(8, 32) 即"32行第8个"。
- 非 16×16 图标用 `assignItemRect(常量, 宽, 高)`；超大贴图（如薄暝 20×20、失乐园 21×20）会超出格子，是预期测试内容。
- **职业护甲图标占 items.png 第 12 行**：`private static final int ARMOR = xy(1,12)`（16 格），依次 `ARMOR+0..+4` 五套普通护甲、`+5..+10` 六职业护甲、`+11` 食指西服（神谕）、`+12` 环指长袍、`+13` 拇指大衣（VALENCINA）、`+14` **中指外套（MIDDLE_FINGER，`xy(15,12)` 16×16）**。新增时：常量声明要写在下面那个 `static{}` 赋值块**之前**（静态初始化按源码顺序执行），并在块内补 `assignItemRect`。
- **自定义职业天赋图标**：为自定义职业新增天赋时，图标一律写在 talent_icons.png 对应预留行，枚举值直接写**绝对索引**并烘焙进枚举，`icon()` 内按 `case <职业>` 特判返回该索引；**禁止**按当前职业对所有天赋做全局行偏移（旧写法 `+7*32` 已废弃）——会让其他职业天赋（枚举图标 ≥64）索引越界 → `TextureFilm.get` 返 null → NPE，蜕变卷轴替换窗口必现闪退。索引位置必须与图内实际绘制一致（历史上出现过两次"整体差 1 格"错位）。各职业已占行与索引见：神谕=第八行（docs/oracle-implementation.md）、环指=第九行（docs/ring-master.md）。
- 英雄/技能图标：`ui/HeroIcon.java`（hero_icons.png 帧号）；buff 图标：`ui/BuffIndicator.java`（连续编号）。新图标需先画进贴图再引用，否则显示空/错位。各职业已分配的 hero/buff/talent 图标索引见对应档案：环指→docs/ring-master.md、神谕→docs/oracle-implementation.md。
- **动画贴图复用**：`index.png` 与 `guard.png` 同规格（256×16、12×16 帧）时直接照抄 `GuardSprite` 换 `Assets.Sprites.INDEX` 即可。

- **音效 = `assets/sounds/*.mp3`（现 101 个，**全部 mp3**），音乐 = `assets/music/*.ogg`（流式播放）**，两者都放在 `core/src/main/assets/` 下，是**唯一真源**：Android 由 `android/build.gradle` 的 `sourceSets.main.assets.srcDirs` 直接指向它（进 APK 的 `assets/sounds/…`），桌面由 `desktop/build.gradle` 的 `processResources { from core/src/main/assets }` 倒进 jar **根目录**（所以 jar 里是 `sounds/…`、**没有 `assets/` 前缀**，核验时别照 APK 的路径找）。**新增音效三步**：①mp3 放进 `core/src/main/assets/sounds/`（小写 snake_case，如 `jelly_boing.mp3`）；②`Assets.Sounds` 里加 `public static final String XXX = "sounds/xxx.mp3";` **并且必须把这个常量加进同类的 `all[]` 数组**；③在触发点 `Sample.INSTANCE.play( Assets.Sounds.XXX )`。**漏掉第②步不会报错**：`Sample.play(id,…)` 的 `id` 就是**资源路径字符串**、同时充当地图 key（`Sample.load` 用同一字符串 put），查不到就静默 `return -1` ⇒ 表现为「改了代码、没声音、日志干净」。`ShatteredPixelDungeon.create()` 里 `Sample.INSTANCE.load(Assets.Sounds.all)` 只是**入队**，真正解码发生在 `Game.update() → Sample.update()`，**每帧只取 1 个**（101 个音效约 1.7 秒加载完），所以开局极早期播放可能还没就绪。播放 API 在 `com.watabou.noosa.audio.Sample`：`play(id[, volume[, pitch]])`、`playDelayed(id, delay, volume, pitch)`（`pitch` 是变速变调，给同一次效果做随机化最省事）；音效开关与音量由 `SPDSettings.soundFx()` / `SFXVol()`（0-10，平方曲线）在启动时灌进 `Sample.INSTANCE.enable()/volume()` ⇒ **新音效自动受设置面板控制**，不必自己判断。**格式取舍**：**扩展名必须与真实容器一致**——桌面后端（lwjgl3）是**按扩展名**挑解码器的（`com.badlogic.gdx.backends.lwjgl3.audio` 下的 `Mp3$Sound` / `Ogg$Sound` / `Wav$Sound`），Android 则由 `SoundPool` 解；一个 MP4/AAC 文件即便改名成 `.mp3` 也照样读不出声（拿 `ffmpeg -i` 一验就露馅：真身是 `mov,mp4,m4a…` + `aac (LC)`，而 `-f mp3` 强解直接 `Conversion failed`）。转码用本机现成的 ffmpeg 即可（`C:\Program Files\Kuyo\ffmpeg.exe`，gyan.dev 完整版，带 `libmp3lame`）：`ffmpeg -y -i in.mp4 -vn -ac 1 -ar 44100 -c:a libmp3lame -b:a 64k out.mp3`。本库音效统一 mp3 且体积极小（多数 <10KB、时长 <1.5s）；`Sound` 是**整段解码进内存**的，别放长音频，`.wav`/`.ogg` 虽也能加载但别用。**「独占音效」**（2026-09-17 果冻音效引入）：`Sample.playExclusive(id, volume, pitch, duration)`＝**从头**播放（先 `Sound.stop()` 掐掉正在播的同一音效，因为 `Sound.play` 是叠加式的、不 stop 会两只一起响）＋**播放期间暂停 `Music`**＋到点自动恢复；`exclusivePlaying()` 问「是不是还在播」。计时挂在 `Sample.update()`（`Game.update()` 每帧无条件调用、与当前场景无关）⇒ 中途切场景也一定会把音乐放回来；只有「暂停是本方发起」时才由本方恢复（`exclusiveOwnsMusic`），窗口失焦/切后台之类的外部暂停不会被误恢复。**注意 `Sample.update()` 里 `delayedSFX` 空时会提前 `return`**，独占计时必须写在它**之前**。自检：`python _chk/audio_format_check.py`（裸解析帧头，打印每个音效的采样率/声道/码率/时长/体积）。

- **地图贴图＝「分层 tilemap + 跨格拼帧」**（2026-09-18 调研，核心类是 `tiles/` 包）。图集 `assets/environment/tiles_*.png` 是 **256×256＝16×16 帧网格、每帧 16×16px**，`DungeonTilemap extends Tilemap` 用 `TextureFilm(tex, 16, 16)`；`DungeonTileSheet` 用 `xy(列,行)`（**1 基**，与物品图标同规则）按"同一地形的不同图层角色"分行：**行 1-3 地面/水/深渊、行 4-5 FLAT_*（平面版）、行 6-9 RAISED_*（抬高地形本体）、行 10-12 WALL_INTERNAL_*（墙内部，全黑）、行 13-14 WALL_OVERHANG_*（墙檐）、行 15-16 DOOR/OTHER 的 OVERHANG 与 UNDERHANG**。`Tilemap.updateVertices()` 只是把第 (col,row) 格的 quad 铺在 `(col*16,row*16)`，**帧本身永不越格** ⇒ 任何"比一格高"的视觉都必须靠**相邻两格各画半截**拼出来。
  - **三个同 map 的 tilemap，靠 z 序+不同帧分工**（`GameScene.create()` 里的装配顺序）：`DungeonTerrainTilemap`（在 `terrain` 组，**处于角色之下**）画地面+抬高地形本体+墙的正面；`RaisedTerrainTilemap`（**在角色之上**）画抬高地形的"下悬"；`DungeonWallsTilemap`（**在角色之上**）画墙内部黑块+**上一格**的"墙檐/草檐"。层序实测：`terrain(water→tiles→customTiles→visualGrid→terrainFeatures)` → `levelVisuals` → `floorEmitters` → `heaps` → `mobs`(hero) → **`raisedTerrain` → `walls`** → `customWalls` → `levelWallVisuals` → `wallBlocking` → `fog`。
  - **一个高草格会被画 5 遍**（缺省非 ALT 帧的清单，来自 `_chk/grass_sandwich.py` 实测）：① `DungeonTerrainTilemap` → `RAISED_HIGH_GRASS` **122 = `xy(11,8)`**（草皮，整格）；② `TerrainFeaturesTilemap` → **第 `9+16*stage` 帧**（halls 0-4 期→`xy(10,1)`/`xy(10,2)`…，在 **terrain_features.png**，草丛整株占 0~14 行）；③ `mobs` 角色贴图；④ `RaisedTerrainTilemap` → `HIGH_GRASS_UNDERHANG` **250 = `xy(11,16)`**（本格，占 0~10 行）；⑤ `DungeonWallsTilemap` → `HIGH_GRASS_OVERHANG` **234 = `xy(11,15)`**（**画在本格、来源却是下方那一格**，占 8~15 行）。**注意 ② 与 ④ 的第 0~10 行是同一批像素**：features 在角色之下先画一遍当背景，raised 再在角色之上画一遍 ⇒ 站进草里时上半截"糊"在身前，正是这个重复绘制造成的。
  - **「两格高的草」＝三件事叠加**（已用像素级复刻核验，见下）：①**拆帧**——草丛总高约 19px，被切成 `HIGH_GRASS_UNDERHANG`（OTHER_OVERHANG+18，**只画第 0~10 行**）与 `HIGH_GRASS_OVERHANG`（+2，**只画第 8~15 行**）；②**跨格**——UNDERHANG 画在草格自己、OVERHANG 画在**上面那一格**（`DungeonWallsTilemap` 在 y-1 格判 `map[pos+mapWidth]==HIGH_GRASS` 得到），两帧在屏幕空间连成一条连续草叶带 ⇒ 视觉上顶到上一格中部；③**z 错位**——草皮 `RAISED_HIGH_GRASS` 在 terrain 组（角色之下）、草叶在 raised/walls 组（角色之上）⇒ 产生遮挡纵深。**⚠️ 算遮挡前必须复刻 `CharSprite.worldToCamera` 的落点**：`perspectiveRaise = 6/16`（`sprites/CharSprite.java:77`）⇒ `y = (行+1)*16 - 贴图高 - 6`，即 **16×16 的格子只有 12×15 的角色贴图被整体抬高 6px，占 world y = 行*16-5 ~ 行*16+9**：**头探进上一格 5px、脚离本格底 6px**。这就是为什么"草能藏人"——抬高 6px 正好让角色**陷进草叶带**里。按正确落点实测（`_chk/grass_sandwich.py`）：
    - 英雄站**高草格本体**（其上一格、下一格也是高草）：被盖 **88/122 px ≈ 72%**——`r0~r4`（头/肩）来自**他自己脚下那丛草的 OVERHANG**（画在**上一格**里，见下条），`r5~r14`（身体/腿）来自本格 UNDERHANG；只余零星像素透出。
    - 英雄站**普通地面**、上一格与下一格都是高草：被盖 **7/122 px ≈ 6%**，只有 `r13~r14`（脚尖），来源是**下方那格**的草 OVERHANG（它只往上探 8px）。
    - **上面那格的草对英雄零影响**（它的 UNDERHANG 在 world `(行-1)*16+0~10`、OVERHANG 落在**再上一格**，与英雄贴图顶边差 1px 擦肩而过）⇒ 「上下都是高草」里**只有下方那格参与遮挡，上方那格纯背景**。
    - 注意 **OVERHANG 的种子取的是「草格自己的 pos」**（`walls_visual` 里传 `pos+mapWidth`）⇒ 同一丛草在「本格 UNDERHANG」与「上一格 OVERHANG」拿到的 ALT 变体一致（122/125、250/253、234/237 配对），上下两块不会错版。换行/加新地形照这个套路：**图集里补 FLAT / RAISED / WALL_OVERHANG / WALL_INTERNAL 四组帧 + 三处 `getTileVisual` 分支**（本作钻石矿墙 `MINE_DIAMOND` 就是这么接的，帧号 256~287 在两行扩展区，见 docs/features.md）。
  - **新增一种地形（尤其草皮）的完整流程见 `docs/terrain-creation-guide.md`**（含手绘速查表、逐帧核验工具、常见坑）。**画房间地形（而不是画贴图）用 `docs/terrain-editor-guide.md` 里的可视化编辑器**（`tools/terrain-editor/index.html`，双击即用，能直接生成可编译的 `StandardRoom.paint()`）。本文档只留四条最容易漏的红线：
    1. **一个楼层只能有一张图集**：`DungeonTerrainTilemap` / `RaisedTerrainTilemap` / `DungeonWallsTilemap` 三者都是 `super(Dungeon.level.tilesTex())` ⇒ 同一张图必须同时供地面、抬高地形、墙、门、草使用，**不存在「草来自 A 图、墙来自 B 图」**。
    2. **草叶细节层是全局唯一的，不跟你换图集**：`TerrainFeaturesTilemap` 固定用 `environment/terrain_features.png`（256×128＝8 行，按 `stage=(depth-1)/5` 选行：0→高草帧 9/10、1→25/26、2→41/42、3→57/58、4→73/74），**与 `tilesTex()` 无关**。想让草叶也完全自己画 ⇒ 新开一个地形 ID，并且**不要**给 `TerrainFeaturesTilemap.getTileVisual` 加分支（它默认 `return -1`＝该格在这一层什么都不画），把草叶全部画进自己的图集（`Terrain.MINE_DIAMOND` 就是这么做的）。
    3. **`directFlatVisuals` 必须补新地形条目**，否则 `WndInfoCell.cellImage → DungeonTerrainTilemap.tile(pos,tile,flat=true)` 里 `directFlatVisuals.get(tile)` 返回 `null`、传给 `int` 形参**自动拆箱 ⇒ NPE**：表现是**点一下这个格子就闪退**（报错现场离病因最远的一处）。
    4. **帧号的行位置由常量写死**（行 1-3 地面/水/深渊、4-5 FLAT、6-9 RAISED、10-12 内部、13-14 墙檐、15-16 檐/下悬），所以**新图集必须保持这套 16 行布局**。六张分区图集（sewers/prison/caves/city/halls/lob）里"全部空白"的帧共 52 个，其中 21 个是保留或被采矿层占用的（`32` 纯水槽、`76~79`、`132~143`、`244~246`、`252`），**真正可随便用的只有 31 个**（名单见指南 §2.4）；更稳的是走「复制原图集 + 向下追加行」（原 256 帧全保留，新帧从 `xy(1,17)=256` 起），先例 `tiles_caves_crystal.png`（256→288）。
  - **草地分帧的「行 → 世界 y」映射是固定的，高度可自定**（2026-09-18 实测）：`OVERHANG` 帧内 row k → 世界 y = `T-(16-k)`（T＝草格顶边；row15 紧贴 T、row0 在 T 上方 16px）；`UNDERHANG` 与 `terrain_features` 帧内 row k → `T+k`。原版草总高 19px ＝**草地格内 11 行（UNDERHANG row 0..10）＋高出顶边 8 行（OVERHANG row 8..15）**；要加高就加"高出顶边"那一半（OVERHANG 最多用满 row 0..15＝顶格 16px），**别把 OVERHANG 的有效行挪进 0..7**——那一段会被画到*再上面一格*的中上部，看起来像草长到了远处。绘制配方：草皮帧必须**满格 256px 不透明**（半透明会漏出背景）；`UNDERHANG` 前景必须 **alpha=255 实心**（否则透出角色身体，像幽灵），且它的 row 0..10 **直接复制 `terrain_features` 草丛的同一批像素**（实测两者掩码完全一致——原版就是"同一株草丛在角色**之下**画一遍当背景、在角色**之上**再画一遍当前景"）；`OVERHANG` 的 row13..15 用**满宽半透明**做「草皮顶檐」（颜色贴近草皮、row13 是一道暗线），row8..12 才是收窄的草尖剪影。
  - **ALT 变体必须在 `commonAltVisuals` 里登记齐全**：`RaisedTerrainTilemap` 与 `DungeonWallsTilemap` **各自独立**调 `getVisualWithAlts`，只登记一半会让「本格下悬」与「上一格草檐」随机到不同变体 ⇒ **上下两块错版**（原版是三三配对：122/125 ↔ 250/253 ↔ 234/237）。

  - **画完新地形怎么自检**（2026-09-18 新增）：`_chk/terrain_tileset_check.py <png> [<角色>:<帧号|列,行> …]` 按「地形角色」逐帧断言——`ground`/`raised`/`flat` 必须满格 256px 不透明、`overhang` 有效行不该落在 0..7、`underhang` 不该从 row≥8 才开始，并打出 ASCII 供目检；不带帧参数时输出总览＋**所有空白帧号与 x,y 坐标**。`_chk/grass_frame_audit.py` 逐行打印草帧的不透明像素数/平均色，并判定「OVERHANG 与 UNDERHANG 是否互为同一丛草的上下两半」「UNDERHANG 与 features 草丛是否同像素」——**画完新草后拿它对照原版**（改路径/帧号即可）。

- **APK 桌面图标 / 应用名**（2026-09-18 调研，完整指南见 **`docs/android-apk-branding-guide.md`**）。三条最容易踩的：

  2. **`android/src/debug/res/` 是 `main` 的整套副本且会覆盖 main** ⇒ 图标改动必须 **main + debug 各一遍**（4 种 × 5 档 × 2 套，另加两个 ldpi 扁平图）。
  3. **改「显示名」安全，改「应用身份」是灾难**：桌面名来自根 `build.gradle` 的 `appName`（→ `manifestPlaceholders` → `android:label="${appName}"`）；而 Android 存档按 **`applicationId`** 定位（`getFilesDir()`＝`/data/data/<pkg>/files/`，偏好文件名还是硬编码的 `"ShatteredPixelDungeon"`）⇒ 改 `appName` **不影响移动端存档**，改 `appPackageName` 等于换一个 App、老存档全成孤儿。另注意 debug 变体带 `applicationIdSuffix ".indev"` ⇒ debug/release 是**两个独立 App、两套独立存档**，别误判成丢档。**桌面端例外**：`DesktopLauncher` 的数据目录原本拼的是 `%APPDATA%\.mypd\<title>\`、而 `title` 就是 `appName` ⇒ 改名会让桌面老存档变孤儿；已把目录名冻结成独立的 `saveDir` 常量（与显示名解耦，改产品名不再动存档路径）。

## 4. SPD 框架机制经验

- **永久 buff**：`Buff.affect` 不带时长会立刻分离（FlavourBuff）；永久效果用大时长（`99999f`）或覆写 `act()`。
- **每回合逻辑**：`Buff.act()` 默认 `diactivate()`（不走 TICK）；覆写 `act()` 时记得 `spend(TICK); return true;`。
- **无视护甲伤害**：`Char.damage(dmg, src)` 不结算护甲（用于"无视防御"类攻击）；普通攻击走 `attackSkill/defenseSkill/drRoll` 全流程。
- **三个「对英雄生效」的宿主钩子**（2026-09-12「泪锋的加护」用；都是就地扩展 Hero/KindOfWeapon 里已有的方法，无需新事件系统）：①**护甲最低减伤** → `Hero.drRoll()` 里 `belongings.armor()` 那段的 `Random.NormalIntRange(DRMin(), DRMax())`：要「只抬保底」就抬 `DRMin` 侧，并**必须补 `if (armMax < armMin) armMax = armMin;`**，否则区间反了；②**受击计数** → `Hero.damage(int, Object)` 中 `if (effectiveDamage <= 0) return;` **之后**（`preHP = HP + shielding()` 已把护盾算进 effectiveDamage ⇒ 被盾完全吃下的那一下也算「受击」），但**必须过滤 `src instanceof Char`**，否则流血/毒/燃烧这类每回合跳一次的 DOT 会瞬间把计数刷爆；③**只削武器攻击力上限（不动下限）** → `KindOfWeapon.damageRoll(Char)` 里 `Hero.heroDamageIntRange(min(), max())`：只削 `max()` 侧、削到低于 `min()` 时取平，注意此处是 augment / 力量加成**之前**的原始掷值（`MeleeWeapon.damageRoll` 在其上再乘 augment）。
- **「受伤充能 / 击杀充能」两个事件钩子**（2026-09-13「复仇账簿」用）：①**受伤量** → `Hero.damage()` 已在算 `int effectiveDamage = preHP - postHP;`（`preHP = HP + shielding()`）：若只想要**真正从 HP 扣掉的血**（护盾吃下的不算），另外自己前后各存一份**不含护盾**的 `HP` 快照再相减，位置放在该行之后即可；②**击杀** → `Mob.die()` 里 `if (cause == Dungeon.hero || cause instanceof Weapon || …)` 的英雄击杀分支（与 `TinyGalaxy/SmilingBlade/RingMasterLoot.onEnemyKilled` 同处），**必须在 `super.die()` 之前**读 `mob.HT`（之后 HP 归零、精灵被回收）。两处都无需新事件系统。
- **「命中 / 未命中」两个事件钩子**（2026-09-14「仔细看好！」用）：`Char.attack` 里命中分支与 else 分支各一处。**命中钩子放在 `enemy.damage(effectiveDamage, this)` 之后**——只有那里才读得到「本击是否击杀」（`!enemy.isAlive()`）；未命中钩子放在 else 分支 `onHeroAttackResolved` 之前。两个钩子共用 `Char.attack` 内的 `this == Dungeon.hero` 判定即可强转 `(Hero) this`（同 577/675 行的既有写法）。**相关数值汇聚点**：精准乘区只在 `Hero.attackSkill()`、力量只在 `Hero.STR()`（这两个是全工程唯一入口，加 buff 加成都写在那里）。**要按"这一击打了多少伤害"判定**（2026-09-16「如数奉还」）就直接用同作用域里的 `effectiveDamage`（第 554 行声明、`enemy.damage(effectiveDamage, this)` 的那个值，已含护甲减免 / 易伤 / 攻防 proc），把它当参数传给需要它的钩子即可——**别再自己前后快照 HP 相减**，那会把「打到护盾上」「目标残血被溢出击杀」这类情况算成不同的数。
- **「攻击命中」其实有两条互不重叠的路，做「挨打就记一笔」类特性必须两条都收口**（2026-09-17「怨恨标记」补远程）：①**近战 / 投掷武器** → `Char.attack(...)` 的命中分支（4 参 `hit(this, enemy, accMulti, false)`，`Hero.shoot` 的投掷也在这里）；②**远程 / 法术弹道** → **`Char.hit(Char, Char, boolean)` 这个 3 参重载**。各法杖怪的 `zap()` 都是 `hit( this, enemy, true )` + `enemy.damage(dmg, new XxxBolt())`（萨满 / 术士 / DM100 / 元素 / 眼魔 / 尤格之爪 / 尤格之拳 / 哨戒室哨兵），**根本不过 `Char.attack`**；3 参重载只有这些调用方（全仓 11 处），所以它是「远程弹道」的天然收口点，一处即覆盖全部（日后新怪也不会漏），且与 4 参重载互不重叠、不会重复叠层。3 参重载里的 `magic ? 2f : 1f` 是「魔法弹道命中加成」，别当成命中率。**代价**：命中判定早于伤害结算，这里拿不到「这一击打了多少」——要按伤害判档的追加效果只能留在 4 参那条路（`Char.attack` 里用 `effectiveDamage`）。
- **「按最终伤害做夹取」的天赋必须先扣掉护盾，否则等于给护盾也上了保命**（2026-09-17「过人的毅力」修正）：护盾是在 `Char.damage` 里**伤害定稿之后**由 `ShieldBuff.processDamage → absorbDamage` 消耗的（`Hero.damage` 里 `dmg` 已定稿、护盾一点没动），所以在 `Hero.damage` 中段夹取 `dmg` 会把护盾那一份也削掉——护盾「本该吃满却没吃满」，等于替盾也挡了刀。正确口径：`absorbed = min(dmg, hero.shielding())`（用 `super.damage` 之前的 `shielding()`，与 `processDamage` 的吸收量完全一致），只对 `dmg - absorbed` 这一部分做夹取，返回 `absorbed + capped`。**饥饿伤害（`src instanceof Hunger`）绕过护盾**，`shielding()` 要按 0 传，否则口径与结算不一致（`Hero.damage` 里 `preHP` 那两行也是这么特判的）。
- **武力戒指的「+N」在伤害公式里是等级 N+1，且等级 ≤0 会被当成诅咒**（2026-09-17「傲人肌肉」踩坑）：`RingOfForce.damageRoll` 的等级来自 `getBuffedBonus → RingBuff.buffedLvl() → soloBuffedBonus()`，而它（未诅咒时）返回 `buffedLvl()+1` ⇒ **+0 戒指 = 等级 1**、+1 戒指 = 等级 2。另外 `min()/max()` 里有一句 `if (lvl <= 0) tier = 1; //tier is forced to 1 if cursed`（**原版就有，不是 mod 加的**）——等级为 0 时 `tier(hero.STR())` 被整体丢弃，伤害钉死 1~10、**力量一概不算**。所以任何「伪造一枚 +N 武力戒指」的实现（如「傲人肌肉」）伪等级必须填 **N+1**；填成 `点数-1` 就会在 +1 点时掉进诅咒分支，比空手还弱、且「仇怨」那 +12 力量完全看不到。
- **「无法闪避」类天赋必须照抄磐岩附魔的两处结构**（2026-09-14「你犯规了」）：①`Hero.defenseSkill()` 末尾 `return 0`（`defRoll` 恒 0 ⇒ 必中），但取「真实闪避值」时要用一个**自己的 testing 开关**跳过归零（磐岩用 `Stone.testingEvasion()`，天赋不要复用它的开关，免得两者互相干扰）；②**`FloatingText.getHitReasonIcon()` 必须补一条 `defRoll == 0` 的早退**——那里原本只对磐岩附魔早退（`defRoll == 0 && arm.hasGlyph(Stone)`），不走早退就会进入 `arm.evasionFactor(...)` 段、拿归零后的 `defenseSkill()` 当分母 ⇒ **0/0 = NaN** 污染命中原因 map（`Collections.sort` 的比较器返回 NaN 还会破坏传递性），并且该 map 的结果最终会变成伤害浮字图标（`Char.damage` 里读 `hitMissIcon`）。③防御侧的换算写在 `Hero.defenseProc(Char enemy, int damage)`（**唯一同时拿得到攻击者与伤害的防御侧钩子**，磐岩也是走这条路）；若防御方护甲本身带同一附魔要**跳过**，否则同一笔算两次。
- **「等待时获得 X」的两种完全不同的实现——先分清要的是「护甲」还是「护盾」**（2026-09-14「你犯规了」+2 踩坑）：**护甲**走 `Hero.drRoll()`（每回合重掷的随机减伤；原版 `HoldFast`「坚守阵地」就是这条，也正因此中文里「等待时获得护甲」几乎是它的专用说法）；**护盾**走 `ShieldBuff` 子类，在 `Char.damage()` 里由 `ShieldBuff.processDamage → absorbDamage` 被消耗。**判定标准只有一个：它会不会被打光**。三个配套要点：①`ShieldBuff.setShield()` **只抬高不降低**（要累加得用 `incShield`）⇒「不可叠加」用它天然成立；②**补盾钩子绝不能写成每回合轮询**（`act()` 里 `if (等待) refresh`）——等待期间每回合补满 = 常驻减伤，手感立刻变成护甲；正确做法是挂在**产生等待的那个入口**（`Hero.rest(boolean fullRest)`，单击等待与长按休息都经过）补**一次**，让护盾成为一次性资源；③解除判定要用「本回合在执行动作」：`Hero.act()` 开头**先取 `curAction != null` 的快照**再进 `if/else`——各 `actXxx()` 分支末尾会把 `curAction` 置回 `null`，之后再判就恒为 false。另注：`Hero.resting` 只代表**长按休息**（单击等待是 `rest(false)` ⇒ `resting = false`），任何「等待时…」的特性只盯 `resting` 都会漏掉单击等待。
- **新增职业天赋时的三重注册**（2026-09-14 中指长兄 T1）：`Talent` 枚举加常量（图标写**绝对索引**）→ `icon()` 的 `HEROIC_ENERGY` 分支加 `case <职业>` → **`initClassTalents` 的三个 tier switch 每个都要显式 case**。第三点最易漏：三个 switch 的首个分支都是 `case WARRIOR: default:`，漏加就会让新职业**白拿战士天赋**；尚未实现的天赋层级写**空 case**（`break;` 什么都不加），`TalentsPane` 会因 `talents.get(i).isEmpty()` 自动跳过空层，比填占位天赋干净。
- **限时数值的「覆盖式刷新」写法**：要「再次触发直接重置时长、不叠层」，把剩余时长设为 `turns` 用 `spend(turns - cooldown())`（`Actor.spend/cooldown` 都在同一套 `time - now` 语义里，先例 `AdrenalineSurge.reset`），别用 `Buff.prolong`（那是叠加）。
- **「冷却型天赋」的标准范式**（2026-09-15 中指长兄 T2「趁手玩具」）：①冷却用一个 `FlavourBuff` 子类（`public static class XxxCooldown extends FlavourBuff{}`，放 `Talent` 里），`Buff.affect(hero, XxxCooldown.class, N - 1f)` —— **减 1** 是因为本回合自身也占一格（原版 `KindOfWeapon.doEquip` 的 `SwiftEquipCooldown` 用 19f 表达「每 20 回合一次」，是最现成的先例）；②判定集中写在 `Talent` 的静态方法里**返回「本次的代价」**（0 = 免费并已开始冷却 / 1 = 正常），调用方只负责 `hero.spendAndNext(cost)`；③**冷却必须在「这一次免费」上就开始**，不能等冷却结束了才记，否则连点两下会白嫖两次；④想让它可见就给 `icon() { return BuffIndicator.TIME; }` + `iconFadePercent()`（照 `RejuvenatingStepsCooldown`），否则玩家无从知道为什么这次没有被免费。
- **「以英雄为源的伤害」怎么判定**（2026-09-15「报复对象」+20% 用）：`Char.damage(int, Object)` 里的 `src` — ①近战、投掷武器、以及所有写 `enemy.damage(dmg, hero)` 的技能，`src` **就是英雄本人**（`src instanceof Hero`）；②但**法杖的 `src` 是法杖实例而不是英雄**（每个法杖都写成 `ch.damage(damageRoll(), this)`），要让法杖伤害也算「英雄打的」就得额外认一类 `Wand`（安全：游戏里只有英雄会真正用法杖打出伤害，DM300 只借 `WandOfBlastWave.throwChar` 做位移、元素怪走 `CursedWand.effect(null, ...)`）；③**间接伤害不算**——点燃地面后的 `Burning` 烫伤、中毒、流血，`src` 是那些 buff 自己。判定要收敛到 `Talent` 的一个静态方法里，别在 `Char` 里摊开写。
- **`Buff.announced = true` 会自己弹名字，不要再手工弹一次**：`Char.add(Buff)` 在 `sprite != null && buff.announced` 时按 `type` 自动 `showStatus(名称)`（POSITIVE→绿、NEGATIVE→橙、NEUTRAL→白），**对怪物同样生效**。所以「给敌人打标记」这类 buff 只要 `announced = true`，头顶就会自己冒出名字；再自己 `sprite.showStatus(...)` 会**弹两遍**。

- **「卸下即还原形态」的类替换写法**（2026-09-13「封印之剑」系列原用；配合 §7 的 `MorphWeapon.morphInto` 类切换）：形态是**独立类**时，「取消装备要变回初始形态」必须在 `doUnequip(Hero,collect,single)` 里**先把武器槽与快捷栏的引用整体换成新实例**（数据照 `morphInto` 那套复制），再让**那个新实例**去走正常卸下流程——因为 `KindOfWeapon.doUnequip` 是靠 `hero.belongings.secondWep == this` / `belongings.weapon == this` 判断该清哪个槽位的，**先换引用才能让槽位被正确清空**，否则槽位会残留旧实例。被诅咒而无法卸下时（`cursed && hero.buff(MagicImmune.class)==null && (!belongings.lostInventory() || keptThroughLostInventory())`）要**提前跳过换引用**，把失败判定原样交给 `super`。

- **神器的"等级"不要覆写 `level()`**（2026-09-15）：`Artifact.visiblyUpgraded()` 是 `level()*10/levelCap`，而神器 `levelCap` 默认为 **0** ⇒ 让 `level()` 返非 0 会得到 `Infinity`（`Math.round` → `Integer.MAX_VALUE`），格子角标直接炸。要"随英雄等级成长"的等级请另开只读方法（如 `ledgerLevel()`），显示靠自己的 `info()`/`status()`。同理：`Artifact.status()` **只在上限恰好 100 时**才显示 `%d%%`，上限会变（100→200）时必须覆写 `status()`，否则退化成 `87/150`。

- **「最终伤害值的最后一刀」只能落在 `Hero.damage` 的 `super.damage` 之前**（2026-09-16「过人的毅力」用）：`Hero.damage` 里 `dmg = (int)Math.ceil(dmg * RingOfTenacity.damageMultiplier(this) * SilentPrice.damageTakenMultiplier())` 这一行之后，**全部倍率与护甲减伤都已结算完，而护盾/血量还一点没动** ⇒ 这里拿到的 `dmg` 就是「这一下真正要打进去的总伤害」，`TearSword.onHitTaken` 的受击计数也正是挑在这个位置。**要夹取伤害（上限/下限/归零）必须写在这里、且早于 `super.damage`**：血量归零→`die()` 是在 `super.damage` 内部一次性做完的，事后补血根本来不及（同 §6「对已死目标的守卫必须写在调用方」是同一类教训）。放在这一处的另一个好处是**覆盖面自动拉满**——攻击、环境、陷阱、坠落、毒/燃烧/流血 DOT 全都汇进 `Hero.damage`，一处夹取全管住。

- **整幅贴图的「弯曲形变」（果冻/鞭状摆动）＝ 分层绘制，别指望单 quad**（2026-09-15「依旧果冻人」挑战）：noosa 里一张 `Image` 只有**一个 quad**（4 顶点、4 分量），顶点级变换只能做出**刚性错切**（整张图倾斜），想让轮廓真的弯出一条曲线（底边不动、越往上偏移越大）只能把贴图**按高度切成 N 条横带**、每条整体横向平移。实现落在 `com.watabou.noosa.JellyDraw`（**引擎级新增**，`Image.draw()` 在 `jellyAmp != 0` 时改走它；`jellyAmp == 0` 的普通路径零改动），状态与计时在 `Image`（`jellyWobble(amp, dir, duration, freq)` / `jellyOffset()` / 覆写的 `update()` 里递增 `jellyTime`），游戏侧只管在触发点调这一个方法（本项目入口 `effects/JellyWobble`）。**四个必守要点**：①**局部坐标 y=0 是贴图顶边、y=height 是底边**（见 `Image.updateVertices()`）⇒「脚底不动」＝高度比例取 0 在底边，偏移用 `t²` 加权（取每层**顶边**处的 t 才能让最上面一层恰好达到满幅）；**但「t 从脚底起算」只对 xy 成立，UV 必须按同一个 `1-t` 插值**（`vTop ↔ y=0`、`vBot ↔ y=height`，与 `Image.updateFrame()` 同构）——直接拿 t 插 UV 会把 `frame.bottom` 贴到顶边、**整张图上下颠倒**（已踩，2026-09-15 修复）；②**顶点要写进全局共享的客户端 `FloatBuffer`（`Quad.createSet(SLICES)` + put 若干层 + `script.drawQuadSet(quads, n)`）**，一次 `glDrawElements` 画完所有层——既避开了 `Vertexbuffer`（切场景时 `Game.switchScene()` 会 `Vertexbuffer.clear()` 清掉所有已注册缓冲 ⇒ 静态共享的 GL id 会失效），也**不能**顺手改 `Image` 自己的 `vertices`/`buffer`（`ItemSprite` 的钻石剑附魔流光直接读 `vertices` 当遮罩 UV，会被串味；而摆动结束后 Image 仍要用自己那份原始顶点继续画）；③**相邻层要向下多铺 0.25 像素**（UV 同步多取一点）防浮点接缝，**最底层不能多铺**（会采样越出帧外、串到贴图册相邻帧）；④**不要给「已死/未挂场景」的贴图无限期留着 `jellyAmp`**——计时靠 `update()` 推进，挂在被更新的组里就一定会自愈（`Group.update()` 递归全部成员，被回收复用的精灵最多多抖 0.9 秒）。参数标定照 §8「时间常量拿真实移动参数校准」的老规矩：`0.9s × 8 rad/s ≈ 7.2` ⇒ 极值点 3 个（`⌊7.2/π⌋+1`），甩出去→回摆→过冲，而不是 0.1 秒抖完的「假摆动」。**分层数要跟着幅度走**：相邻层错位量＝`2·amplitude·t / SLICES`，幅度调大而不加层，峰值处轮廓会露出阶梯（现取 `SLICES = 20` / `AMP = 16`，由 `effects/JellyWobble` 标定）。**竖直形变要和横向叠在同一套零点上**：`y = h·(1 − t·(1+squash))` 把「压扁/拉长」也锚在底边，再把压扁量按 `t` 折算成横向鼓出（`BULGE`）——横移 / 压缩 / 鼓出三路形变的零点全在底边，「脚底不移动也不形变」才不会被某一路破坏；竖直必须与横向**差 1/4 周期**（`cos → −sin`），同步缩放只是「呼吸」，不是果冻。**摆动来回次数 = `DURATION × FREQ / (2π)`**（改次数只动这两个常量）。**死亡动画不要**去 28 个 `XxxSprite.die()` 里逐个加（大半会 `super.die()` ⇒ 重复触发），钩在**唯一的** `Char.die()` 里，且必须在 `sprite.die()` **之前**（有的死亡动画会 `killAndErase()` 把精灵摘走）。

- **游戏 BGM 的全局替换钩子 = 引擎层的 `Music.setTrackOverride`**（2026-09-18「角色专属 BGM」）：BGM 的播放点**散落在十几处**（各 `Level.playLevelMusic()`、`YogDzewa`/`DwarfKing` 战斗中途变奏、`AmuletScene` 等），逐个改既容易漏又会污染原版代码。做法是在 `com.watabou.noosa.audio.Music` 里加一个可注册的钩子（`public interface TrackOverride { String override(String requestedTrack); }` + `setTrackOverride`），只在两个**公共入口**生效：`play(String, boolean)` 与 `playTracks(String[], float[], boolean)`。要点：①`override` 返回 `null` **或与请求相同**的曲目都视为「不干预」（这条幂等规则很关键——`playTracks` 命中后内部会再调一次 `play(forced, true)`，幂等才不会打转）；②`playTracks` 命中时整个随机列表被「该曲目单曲循环」取代（`play(forced, true)` 后 `return`，`trackList` 保持 null ⇒ `enable(true)` 重启走 `lastPlayed` 分支，安全）；③`lastPlayed` 记的是**替换之后**的名字，所以开关来回切时能被正确判成「换曲」而重播、同曲时不打断；④**立即生效**＝`HeroBgm.refresh()` → `Dungeon.level.playLevelMusic()`（让当前层重走一遍选曲，请求再经钩子）。游戏侧封装在 [HeroBgm.java](file:///d:/PD/core/src/main/java/com/shatteredpixel/shatteredpixeldungeon/HeroBgm.java)：`track()` 在「开关关 / `Dungeon.hero == null` / 英雄不在四位之列」时一律返回 `null`——于是标题、选人、结算、日志这些 `Dungeon.hero = null` 的界面天然不被替换，**「非专属角色设置里不出现该选项」也直接复用同一个判据**（`WndSettings.AudioTab` 用 `HeroBgm.hasBgm(HeroBgm.activeClass())` 决定要不要 `add`）。**素材规格**：自定义 BGM 走 **mp3**（`core/src/main/assets/music/`，Android/iOS/桌面三端的 assets 都指向 core 这一份），44100Hz / 立体声 / **96kbps**（`_chk/import_hero_bgm.py` 一键转码+体积报表）；`DeviceCompat.isiOS()` 那条 `.ogg → .mp3` 替换对已经是 mp3 的名字没有影响。**`Music` 是流式解码**（gdx `Music` 边读边解），文件体积只影响包体与安装占用，**不影响运行时内存**（对照 `Sample`——音效是整段解码进内存的，见 §4 音频条目）。

- **武器「命中音」的唯一钩子 = `KindOfWeapon.hitSound(float pitch)`，不是 `hitSound` 字段**（2026-09-18 双蛇杖随机攻击音）：调用链是 `Char.attack` 命中分支 → `Hero.hitSound(pitch)` → **`belongings.attackingWeapon().hitSound(pitch)`**（多态）→ `KindOfWeapon` 里 `Sample.INSTANCE.play(hitSound, 1, pitch * hitSoundPitch)`。要点：①**改 `hitSound` 字段 ≠ 改行为**——字段只能填**一条固定音**，而且下面那条会让它**根本不被读到**，所以「每次命中随机播一条」这类需求只能**覆写方法**；②**`attackingWeapon()` 的取值顺序是 `thrownWeapon` → `abilityWeapon` → `weapon()`**，而 `MeleeWeapon.beforeAbilityUsed` 会写 `hero.belongings.abilityWeapon = this`（`afterAbilityUsed` 复位）⇒ **武技窗口内 `attackingWeapon()` 是被委托执行武技的那把武器**；对「会变形/会委托」的武器（双蛇杖把武技转给随机形态武器）来说，这段时间听到的是**形态武器自己的命中音**，变形武器配置的音被整体绕过 ⇒ 必须在武技入口同步过去（`KindOfWeapon` 为此加了 `setHitSound(String)`，因为 `hitSound` 是 `items` 包的 **protected**、`items.weapon.melee` 跨包写不了；对照 `augment` 是 public 才能被 `formInstance.augment = ...` 写）；③**只在「命中」分支触发**（`effectiveDamage > 0 || !enemy.blockSound(...)`），未命中走 `Assets.Sounds.MISS`；④**技能里直接 `enemy.damage(dmg, src)` 的伤害不经过 `Char.attack`，因此完全不出命中音**，要出声必须自己 `Sample.INSTANCE.play(...)`（Furioso-Replica 九连击就是这种情况）。**新增音效资源三件套**：`Assets.java` 加常量 → **必须同时塞进 `Sounds.all[]`**（漏了就是静默无声，`Sample.load` 只认这张表）→ 文件放 `core/src/main/assets/sounds/`；规格照项目惯例 **mp3 / 44100Hz / 单声道 / 64kbps / ≤2s**（长于 2s 的如 jelly 5.9s 是特例）。响度建议用 `_chk/import_lcb_sfx.py` 的量测+闭环归一：项目现有音效是**均值 −18.9~−22.6 dB、峰值 −2.5~−3.8 dB**，直接拿外部素材入库会因录制电平差出 6 dB。
- **角色语音 = 一个「每角色一个入口类」+ 六条铁律**（2026-09-18 拇指 `ValencinaSfx` / 中指 `MiddleFingerVoice` / 环指 `RingMasterVoice`）：
  入口类放**该角色技能所在包**（`actors/hero/abilities/<角色>/XxxSfx|XxxVoice.java`），把「素材、触发条件、去抖」全收在一处，调用方只写一句。
  ①**语音与头顶文本必须成对**：做成 `text + sound + duration` 三元组（`Line` 小对象或 `String[][]`），一次取用、同时播；
  拆成两张表各自随机就会出现「显示 A、念的却是 B」。
  ②**「上一条没播完就整条跳过」**：`Sound.play` 是**叠加式**的（不打断上一条），连击/连续受击时不拦就会糊成一团。
  判据 `lastAt > 0 && Game.timeTotal > lastAt && Game.timeTotal - lastAt < duration`——时间戳**必须是 `Game.timeTotal`（累计秒），
  不能用 `Game.elapsed`（每帧增量 ≈0.016s，当时间戳用差值恒为负、去抖直接失效）**；前半条件应对游戏重启（`timeTotal` 归零而静态字段仍是旧值）。
  ③**每条素材的时长要量出来写死**（`Sample` 不提供「还剩多久播完」的查询）：`ffmpeg -hide_banner -i x.mp3` 读 `Duration`，
  偏大只是多等一会儿、**偏小会叠音**。`_chk/audio_format_check.py` 报的时长是**按帧数估算**的（比解码实测大 0.07s 左右），别拿它当准。
  ④**入口类自己认人**（`Dungeon.hero.heroClass == Xxx`）：通用钩子（`Hero.damage` 的受击、`SealedSwordBase` 的解封）是所有角色共用的，
  不判职业 = 人人都说这句台词。
  ⑤**「技能演完才播」的台词挂在连段的最后一拍，不是按下按钮时**（对照 `InstantExecution.Execution` 的 `case 5`，
  与 `activate()` 里的「使用时」音效区分开）。
   **「挂在哪」的通用判据**：`Buff.affect` 的**授予处**＝「获得时」（别写进 `FlavourBuff.act()`，它整个生命周期只调一次，见 §6）；`act()`＝「回合开始时」的持续判定（账簿满充能那种）；武器/技能内部＝「使用时」。
  ⑥**语音通道与攻击音效通道必须分开**：语音的去抖窗口是 1~5 秒（上一条没播完就跳过），打击音若共用同一条通道，
  刚喊完台词的那几秒里打击音会被整段吞掉 ⇒ 入口类里另开一个**不带去抖**的播放口（`playStrike()` 之类，
  内部直接 `Sample.play( Random.element(...) )`），素材另起一组常量。语音照旧只受自己的时长约束、打击音每次命中都响。
  ⑦**条件条目**：同一张台词表里可以带「仅在某个条件下才进入候选池」的标记（环指 `Line.tibiaOnly`＝装备「一生之作-提比娅」
  才随机得到「提比娅的旋律」那两条）。判定必须在**每次触发时现算**（`hero.belongings.weapon() instanceof Xxx`），
  **不要缓存**——缓存了换武器就得等下次重新计算才生效。候选池用「遍历+筛选」建，别用 `do{随机}while(不满足)`（后者在极端情况下会死循环）。

## 6. 常见陷阱速查

| 现象 | 原因 | 处理 |
|---|---|---|
| 窗口内暂存物品（已 detach 出背包）切后台/场景重建后丢失（移动端创作/强化/分解/附魔窗口的 bug） | 物品只存在于 UI 字段（已从背包 detach、不可序列化）；`GameScene.onPause()` → `saveAll()` 先于任何退回执行，进程被杀后读档即丢；旋转/尺寸变化重建场景时窗口直接 destroy 也不退 | 持有物品的窗口实现 `windows/WindowReturnsItems`：`destroy()` 覆写先 `returnAllItems()`（兜底一切销毁路径），并提供 `returnItemsAndClose()`；`GameScene.onPause()` 保存前对场景内所有 `WindowReturnsItems` 统一收尾（创作/强化/分解/附魔四窗已接；参考 AlchemyScene.clearSlots 范式） |

| FlavourBuff 秒消失 | `Buff.affect` 无时长 | 用 `Buff.affect(..., 99999f)` 或 `Buff.prolong` |

| 手动攻击不随机形态 | 双蛇杖形态在 `accuracyFactor` 才 roll | 显式调用 `rollFormForAttack()` / `forceScytheForm()` |

| 编辑某个 `.java` 后编译报 `unmappable character` / 中文注释变乱码 | 写入端编码错乱，**同一文件里两种编码混存**（2026-09-17 在 `ClassArmor.java` 一次踩中两种）：① 新写入的中文注释**整行按 GBK 落盘**；② **行尾 3 字节汉字的最后一字节被 clobber 成 `?`**（`衣`=`E8 A1 A3` ⇒ 残留 `E8 A1 3F`，`套`=`E5 A5 97` ⇒ `E5 A5 3F`）。两类都会让文件不再是合法 UTF-8，而 `core/build.gradle` 指定 `options.encoding='UTF-8'` ⇒ **直接编译失败**（且损坏可能出现在**离改动很远**的行上，别只看改动点） | **改完任何 `.java`/`.properties` 立刻跑 `python _chk/check_utf8_all.py`**：全仓扫，任一文件非 UTF-8 即 FAIL，并另报「汉字后紧跟 `?`」的可疑行（合法 UTF-8 时的残留特征）。修复样板 `_chk/fix_classarmor_encoding.py`：按 `utf-8 + surrogateescape` **无损**读入 → 只替换出事的那几行（唯一性断言 + 逐行打印新旧）→ 写回后再断言「可完整解码 / 无代理字符 / 关键内容在」。**不要**再用「整文件按 GBK 解码再写 UTF-8」的老办法——混存文件会报错或二次污染 |

## 7. 自定义武器/物品开发经验（通用）

> 原 §7 中环指大师专属的"人体派作品武器 14 把/素材/大师指环合成/击杀掉落"大段已移至 docs/ring-master.md（本节的通用条目与"装备中物品不可加入合成/强化/分解"防复制修复保留）。

- **新增武器创作指南**：手动创建普通新武器的步骤式流程（类文件/空位图标/绘制/消息键 zh+en/入掉落池/编译验证/归档）见 docs/weapon-creation-guide.md；纯面板+图标可自行完成，特殊功能（引擎钩子类效果）交 AI 实现并必须记录实现位置。

- **武器类**：继承同阶/同武技的原版武器类即可"套用武技配置"（如 `RedEye extends Cudgel`、`LingeringScent extends Crossbow`），`tier` 在实例块覆写；`min/max` 显式给出公式；`DLY`（延迟）/`RCH`（距离）/`ACC`（命中）/`hitSound` 在实例块覆写。武技文本沿继承链回退到父武器。
- **入掉落池**：`Generator.java` 的 `WEP_T2/3/4.classes` + `defaultProbs` 显式列表（prob=2 与原版同级武器同权，胎儿博士为 1）。
- **物品图标**：`ItemSpriteSheet` 用 `xy(行,列)`（1 基）+ `assignItemRect(常量,宽,高)`；非 16×16 用实际尺寸。贴图未画/画错位置→游戏里显示空白（可用 PowerShell System.Drawing 逐像素扫描验证）。
- **物品显示常驻粒子**（如附魔光效）：重写 `Item.emitter()` 返回 `new Emitter()` + `pos(偏移)` + `fillTarget=false` + `pour(粒子工厂, 间隔秒)`——`ItemSprite` 会在地面/背包/快捷栏显示时自动挂载并管理生命周期（`killAndErase`）。参考 `SpiritBow` 箭矢的树叶粒子。
- **受击特效**：命中时在目标身上播放的粒子，触发点放 `Char.defenseProc`（目标自身方法，攻击链最前），`enemy` 参数即攻击者（`enemy instanceof Hero` 后查其 `belongings.weapon()/secondWep()`）。圣宣蝴蝶即此方案成功。
- **装备时特效**：`Item.activate(Char)` 挂 buff（equip 时调用，副手也调）、覆写 `doUnequip` 卸下时移除；buff `act()` 里用常驻发射器按血量/状态调整 `emitter.start(factory, interval, 0)`。
- **等待动作钩子**：`Hero.rest(boolean fullRest)`（余香"等待获得花矢"）；**飞镖耐久**：`TippedDart.decrementDurability()` 覆写（触发一次免费使用后移除 buff）。
- **伤害浮字图标**：`Char.damage` 按 `src.getClass()` 决定图标（`AntiMagic.RESISTS` → `MAGIC_DMG` 等）；按击切换可用武器上的静态标记：`Char.attack` 置位 → `Char.damage` 图标判断 → 伤害结算后复位。法杖类伤害=直接 `ch.damage()` 绕过护甲（无"伤害类型"系统），武器等效实现为 `dr=0`。
- **自定义 buff 图标**：`BuffIndicator.HEART_FATE+1`（花矢=93）等连续编号，需先在 buff_icons.png 绘制。
- **消息格式**：氛围文本（`desc`）与功能性文本（`stats_desc`/`typical_stats_desc` 等）**分开写入**；带占位符的 `stats_desc` 用 `_%1$d_` 且**字面 % 必须 `%%`**；`typical_stats_desc` 供未鉴定时显示（可覆写 `statsInfo()` 不区分鉴定状态）。
- **粒子类**：自定义 `PixelParticle` 子类（模型参考 `HeartFateParticle`/`PinkParticle`）；可复用 `Assets.Effects.SPECKS` 贴图（7×7 帧网格，`TextureFilm(texture,7,7)`，帧16/17=黑/白蝴蝶已绘制）。
- **字母制等级显示**（验证完成，参考 `GradeTestSword extends Shortsword`；已正式用于人体派作品武器，基类 `BodyArtWeapon.levelDisplay`）：只需覆写 `Item.levelDisplay(int buffedLvl)` 返回映射字符串（如 0→"F"、4→"A-"、6→"A+"），**无需动字体/渲染**（pixel_font 已含字母与 `+`/`-`）。要点：①数值/贴图/武技全继承父武器（短剑）即可套用；②负等级（降级）建议回退 `super.levelDisplay()` 走默认 `-N`，因字母制难表达负数；③超出映射区间封顶或回退默认；④未鉴定时 `buffedVisiblyUpgraded` 返回 0，会触发 levelDisplay(0) 显示"F"——会泄露"这是字母制武器"，正式版需在 levelDisplay 里按 `levelKnown` 区分（验证场景可接受）；⑤右下角格子与**名称后缀**（`Item.title()`）都已走 levelDisplay 钩子，自动一致；仍用数字的显示点：WndUpgrade 升级界面（各自 `"+N"` 拼接），需要时另行同步。

- **装备中物品不可加入合成/强化/分解**（2026-09-01 防 bug 修复）：`WndBag`（经 `GameScene.selectItem` 打开）**会展示英雄已装备的 weapon/armor/artifact/misc/ring**（[WndBag.java#L243](file:///d:/PD/core/src/main/java/com/shatteredpixel/shatteredpixeldungeon/windows/WndBag.java#L243) 的 `placeItems`）。若 `itemSelector.itemSelectable` 仅检查 `instanceof` 不排除装备中物品，则已装备武器（如初始 试作-解体刀 BodyArtWeapon）可被选中 → `onSelect` 里 `item.detach(backpack)` 因装备中物品不在背包返 null → 走 fallback `detachAll`+`material=item` → **物品既在装备槽又在合成格=复制**。**修复**：三个窗口的 `itemSelector.itemSelectable` 首行统一加 `if (item.isEquipped(Dungeon.hero)) return false;`（`KindOfWeapon.isEquipped` 检 `belongings.weapon()/secondWep()==this`、`Armor` 检 `belongings.armor()==this` 等，各装备类各自覆写）。要强化/分解已装备武器须先卸下再放入。

- **引擎钩子类武器效果三例（2026-09-06 四阶E.G.O 拘束/盲目/渴望，实现位置备忘）**：

  - 装备型被动 buff 通用写法：`activate` 挂 + `doUnequip` 卸 + 若需兜底可在 `act()` 里自校验装备仍在（参考 `DimDusk.DimDuskAura`）。buff 类与引擎文件撞名时（如 Level 已用 buffs.Blindness）把标记 buff 独立放 `actors/buffs` 包避免 import 冲突。

## 8. 法杖类武器（失乐园）与 buff 特效开发经验

- **"武器+法杖"复合结构**（失乐园）：`MeleeWeapon` 内嵌 `Wand`（构造时 `new WandOfMagicMissile()` + `identify()`），充能走 `Wand.Charger`：`activate/collect` 时 `wand.charge(owner, 0.75f)`、`onDetach` 时 `wand.stopCharging()`、`upgrade` 时 `updateWand(true)`（同步等级与 maxCharges）；施法委托 `wand.execute(hero, AC_ZAP)`。`updateWand` 里 `wand.maxCharges = min(maxCharges+1, 10)` 是老魔杖模式（比普通法杖多 1 上限）。
- **自定义施法效果**（失乐园 onZap）：不复用 `Wand.zapper`（它拦截 self_target），自建 `CellSelector.Listener`：`GameScene.selectCell(zapper)` → onSelect 里 `Ballistica(curUser.pos, target, MAGIC_BOLT)` → `onZap` 分流（敌方/空地=范围伤害、友方/自身=增益）。目标选择 UI 提示走 `prompt()` 返回 `Messages.get(Class, "zap_prompt")`。
- **允许对自身施法**：zapper 里显式 `if (target == curUser.pos)` 直接调效果分支（不走弹道），参考法师储能护盾（SHIELD_BATTERY）的写法。
- **施法后结算**：`curUser.busy()` + 同步 `onZap` + `wand.wandUsed()`（内部 `curCharges -= chargesPerCast()` + `curUser.spendAndNext(TIME_TO_ZAP=1f)`）；无需自绘弹道特效（`MagicMissile.boltFromChar`）——远程直伤的特效在 onZap 里对每个目标显式播放。
- **伤害成长套用**：雷电法杖 `min=5+lvl, max=10+5*lvl`，用 `Random.NormalIntRange`；治疗/护盾套用注魂法杖：友方回血 `round(自身HT*0.05) + 3*lvl`（溢出转 `Barrier` 护盾）、自身护盾 `5+lvl`。
- **buff 百分比属性加成**（祝福）：精准/闪避在 `Hero.attackSkill/defenseSkill` 里乘倍数（参考 HeartFateBuff 的 `accuracyMultiplier/evasionMultiplier`）；**最大生命 +5%** 对 Hero 在 `Hero.updateHT()` 里乘 `HTMultiplier`（attach 时 `updateHT(true)`、detach 时 `updateHT(false)`，buff 移除后重算自动恢复）；对非 Hero 单位直接改 `target.HT/HP` 字段并**存档 htBonus**。
- **buff 文本特殊颜色**（紫罗兰 #EE82EE，与失乐园物品文本一致）：改 `WndInfoBuff` 特判 `buff instanceof 类名` → `titlebar.label(..., 0xEE82EE)` + `txtInfo.hardlight(0xEE82EE)`（同 `WndInfoItem` 对失乐园的处理）。
- **多帧贴图特效**（heaven.png 长矛贯穿）：`Image` 子类 + `frame(texture.uvRect(x1,y1,x2,y2))` 取帧（像素坐标）；`origin` 设底部中心（`origin.set(宽/2, 高)`）实现"底部不动、顶部向上伸展"（`scale.y` 0→1）；**随机选帧**用 `Random.Int(2)` 在 reset 时选一张；生命期用 `Game.elapsed` 递减，`kill()` 结束。
- **跟随单位的标记贴图**（祝福标记/指令目标）：`ItemSprite` 子类（`ItemSpriteSheet.film.get(icon)` 或 `assignItemRect` 注册非标准区域），`update()` 每帧 `place()` 同步到 `target.sprite.center()`（上移像素直接在 place 里减 y）；buff `fx(boolean)` 挂载/销毁，`Char.updateSpriteState()` 读档自动重建。
- **图层顺序**：`GameScene` create 中 `floorEmitters`（角色**之下**）→ `mobs`（角色）→ `emitters/effects`（角色**之上**）。需要贴图在角色之下挂 `floorEmitters`（新增静态方法 `floorEmittersAdd`），之上挂 `effect`。标记贴图不透明就不要调 `alpha()`（指令目标是半透明 `alpha(0.5f)`）。
  - ⚠️ `effect` / `effectOverFog` 形参是 **`Visual`**，而 `Group`(→`Gizmo`) 不是 `Visual` 传不进去；`floorEmittersAdd` 已于 2026-09-11 **放宽为 `Gizmo`**（唯一调用点 `BlessingMarker` 零改动）→ **「渲染在角色之下」现在可直接挂 `Group`**。`GameScene.mobs`/`effects`/`floorEmitters` 都是**私有实例字段**；往角色层挂非 Visual 的 Gizmo 用 `target.sprite.parent.add(gizmo)`（= `GameScene.mobs`，参考 `MasterpieceShow.ensureVisual`）；`sortMobSprites()` 把 mobs 内**非 Visual 成员排到队尾** → 同组但渲染在角色之上。
  - ⚠️ **同一层内无法与角色交错**：要「一部分贴图在角色前、一部分在后」必须拆成两个组挂不同层（`Group.add()` 会自动把节点从原组摘除 → 换层一行搞定）。泪剑「背身层」即此范式：本组挂 mobs（角色之上）+ `behind` 组挂 `floorEmitters`（角色之下），按「是否与朝向同侧」逐帧换层。
  - **全屏屏幕空间滤镜怎么做到「压住画面但不遮 UI」**（2026-09-14 `HeatVignette`）：`Group.draw()` 严格按 `add()` 顺序绘制，而 `GameScene.create()` 里 `add(cellSelector)` 之后就是第一件 UI（`add(menu)`）——把滤镜 `add()` 在这一行**之后、UI 之前**即可（世界层在它下面被着色，状态栏/工具栏/动作条/日志/窗口全在它上面）。它必须自带 `camera = PixelScene.uiCamera`（默认继承 `Camera.main` 会跟着英雄滚动，而「屏幕边缘」要求屏幕空间），并按 `scale = (uiCamera.width/texW, uiCamera.height/texH)` 把贴图拉伸铺满（`Image` 没有 `size()`，改 `scale` 比改 `width/height` 省掉 `updateVertices()`）。渐变色罩用**一张白色径向渐变贴图 + `hardlight(color)` 染色**（片元是 `tex * uColorM + uColorA`，默认混合 `SRC_ALPHA/ONE_MINUS_SRC_ALPHA` ⇒ 按 alpha 给画面掺色）；贴图用 `TextureCache.create(key, w, h)` 后直接写 `texture.bitmap`（libGDX `Pixmap`，**RGBA8888：R 在高位**，要**非预乘**＝RGB 恒白、只让 A 走渐变），不手动上传也安全（`create` 只建对象 `id==-1`，其 `filter/wrap` 见未生成会跳过 GL；真正上传在首次 `bind()`）。
  - **屏幕空间「热浪扭曲」＝换掉全局着色器，别自己开 FBO**（2026-09-14 `NoosaScriptWarp`）：noosa 没有后期处理管线，折射/模糊这类整屏效果的正确做法是**改 shader**——新建 `NoosaScriptWarp extends NoosaScript`（片元里按屏幕位置偏移采样 UV），再让 **`NoosaScript.get()` 与 `NoosaScriptNoLighting.get()` 在开关打开时返回它**：这两处是所有 `Image`/`Tilemap`/`Text` 的着色器汇聚点（`Image.script()` 只有一句 `return NoosaScript.get()`），改一处即覆盖全部世界元素。**「谁被扭曲」靠每帧开/关**：`GameScene.draw()` 的**第一句**打开、**最后一件世界层元素的 `draw()` 第一行**关掉 ⇒ 世界被折射而 UI 纹丝不动，UI 侧无需任何处理。**开关一定要放在 `draw()` 而不是 `update()`**：`Game.render()` 的顺序是 `resetCamera() → draw() → step()(update)`，若在 `update()` 里开关，下一帧开头那两句 `NoosaScript.get().resetCamera()` / `NoosaScriptNoLighting.get().resetCamera()` 也会被换成扭曲脚本，普通脚本的相机缓存就再也清不掉（UI 会用上过期矩阵）。四个坑：①把 `NoosaScriptNoLighting` 的消费者换成带光照的 shader 前，先确认它们传的是**恒等光照**（`Tilemap`/`FogOfWar`/`SkinnedBlock` 都只传 `Visual` 默认值 `rm=gm=bm=am=1, ra..=0`，等价，观感不变）；②**新脚本必须每帧清相机缓存**——`NoosaScript.camera()` 只在相机**对象**变化时才上传 `uCamera`，而 `Camera.main` 是同一个对象、`matrix` 数组是原地改写的，全靠 `Game.render()` 每帧的 `resetCamera()` 才跟得上镜头，新脚本要自己加一句 `XxxScript.resetCameraCache()`（否则画面从此再不跟随相机滚动）；③**别用 `gl_FragCoord`**（部分移动 GPU 只有 mediump 精度，1080p 下误差可达数像素），在顶点里输出 `(uCamera*uModel*aXYZW).xy` 当 `vScreen` 更准也更省；④相位用 `2π` 回绕且**时间系数一律取整数**（1/2/3），回绕点上才连续不跳变。开关关掉时整条链路回到原 shader，零开销。
  - **屏幕空间的粒子（沿屏幕边缘铺火苗）**：`Emitter` 的 `camera = PixelScene.uiCamera` 即变为屏幕空间（粒子坐标直接是 UI 像素），位置用**归一化坐标**每帧换算 `uiCamera.width/height` ⇒ 窗口尺寸变化自动跟随（但 `uiCamera` 在 resize 时会被重建，所以每帧重认一次 `emitter.camera`）。`Emitter` 必须 `autoKill = false`：`update()` 里有 `else if (started && autoKill && countLiving()==0) kill()` —— 一旦 `on=false` 清空它就**自杀且永不复活**，凡是要手动开关的发射器都不能让这条生效。发射参数（颜色/方向/大小）**要为每条线各建一个 `Emitter.Factory`**（匿名内部类捕获方向，颜色/速度在 `emit()` 那一刻从外层现读）：`Factory` 是发射时现取的，若用一个静态 `FACTORY` + 静态字段喂参，几条方向不同的线会在同一帧里互相覆盖。密度调节＝改 `interval` 后 `startDelayed(factory, interval, 0, 0f)`（**`delay=0` 才会立刻产出第一颗**），且**只在变化超过 ±15% 时才重设**——每帧重设会不停重置发射计时器，看起来像零星乱冒。
  - **「跟随角色的持续粒子」别自己 `new Emitter`，借 `CharSprite.emitter()`**（2026-09-14 复仇账簿「仇怨」紫粒子）：`target.sprite.emitter()` 从 `GameScene.emitters` 组里领一个发射器并 `pos(贴图)`（自动跟随移动、`fillTarget=true` ⇒ 在贴图矩形内随机点发射），`pour(factory, interval)` 即持续产出。要点：①**重建判据用 `exists` 而不是 `parent != null`**——`Group.destroy()` 只递归 `destroy()` 子节点、**不清 `parent`**，所以换层后旧发射器 `parent` 仍非空但 `exists` 已是 false；②重建时机不用自己找：英雄贴图重建时 `HeroSprite()` 构造 → `CharSprite.link()` → `Char.updateSpriteState()` 会对**所有 buff** 跑一遍 `fx(true)`，所以把「建/重建」写在 `fx(boolean)` 里、再在每回合 `act()` 里兜底调用一次即可（`GameScene.create()` 里 `scene = this` 早于 `new HeroSprite()`，开局就能拿到发射器）；③停用只写 `on = false`（在飞的粒子自然消亡后由 `autoKill` 自毁），**别 `kill()`**——那会把满屏粒子一下抹掉；④`Buff.detach()` 只在 `target.sprite != null` 时才回调 `fx(false)`，读档期间 sprite 为 null ⇒ 覆写的 `detach()` 里要自己补一次停止；⑤静态常量放外层类（**Java 11：非静态内部类里只允许 `static final` 常量表达式字段**）；⑥「向四周散发」＝`speed.polar(Random.Float(PointF.PI2), Random.Float(min,max))` + 一点上浮 `speed.y -= r`，工厂 `lightMode()` 返 true 走加色混合（`PseudoPixel` 是 1×1 实心贴图，`size(n)` 就是 n×n 像素）。
- **静态 `Image` 要水平镜像只能 `scale.x = -1`**：`Image.flipHorizontal` 是裸 public 字段，只在 `frame()`→`updateFrame()` 时才写进顶点，静态图构造后再赋值**完全无效**（`CharSprite.turnTo()` 敢直接改字段，是因为它每帧动画都会重新 `frame()` 覆盖顶点）。旋转+镜像的组合：noosa 变换线性部分 = `R(angle)·S(scale)`，屏幕 y 向下故**正角=顺时针**（"屏幕逆时针 45°"写 `-45f`）；`R(+45)·S(-1,1) ≡ M_h·R(-45)` 正好是正向结果的水平镜像。**`origin` 是「平移量 + 转轴」二合一**（`updateMatrix()` = `T(x,y)·T(o)·R·S·T(-o)`）：要以**非中心点**为轴（如泪剑的 (5,5)）必须 `origin.set(5,5)` **且**定位写成 `x = 目标点x − origin.x`——两处成对改，只改一处 → 贴图整体偏移/转轴错位。`originToCenter()` 内部即 `origin.set(width/2, height/2)`（用**原始 width/height 字段**，不含 scale），故轴心换成任意点后 `scale.x = -1` 仍以该点对齐（别用 `width()`，那个会乘 `scale.x`、朝左变负）。
- **贴图特效里的「时间」常量要拿真实移动参数标定**：`CharSprite.DEFAULT_MOVE_INTERVAL = 0.1f` 秒/格、一格 16 像素 ⇒ **约 160 像素/秒**（全工程无任何 `setMoveInterval` 调用点，恒为默认值）。凡「延迟 N 秒」「持续 N 秒」的视觉参数，先换算成**像素/格**再定值——否则很容易做出落后两三格的拖尾（残像纠缠的 `DELAY_STEP` 就是这么标出来的：0.07s ≈ 11px ≈ 2.8 格）。
- **场景销毁会递归清 `parent`，可据此判断「视觉是否随场景销毁」**：`Game.switchScene()` → `scene.destroy()` → `Group.destroy()`（先 `super.destroy()` 把自己 `parent` 置 null，再对每个成员递归 `destroy()`）⇒ 挂在 `floorEmitters`/`mobs` 的自定义视觉在换场景后**全部 `parent == null`**，这正是「重建判据写成 `parent == null`」可靠的原因（`fx(true)` 里据此重建即可）。⚠️ `Group.destroy()` 同时把 `members` 置 null ⇒ **销毁过的组不可再 `add()`**（NPE），惰性挂载时 `parent == null` 一律新建组。
- **`Group.recycle(Class)` 只发槽位、不调 `reset()`**：拿到的粒子必须自己 `revive()` + 复位 `am`（`revive()` 只重置 exists/alive，不还原透明度，否则复用首帧会沿用上一世临死时的 `am`）+ 位置/颜色/尺寸。`Group.update()/draw()` 会递归成员，但只处理 `exists && active`。
- **跨组挂载的节点要自己回收；已 `destroy()` 的组不可复用**：把子节点挂到别的组（如 `floorEmitters`）后，它**不再随本组** `killAndErase()`/`destroy()` 一起清 → 覆写 `kill()` / `destroy()` 为「先遍历自己的列表逐个 `killAndErase()`，再 `super`」。`Group.destroy()` 会把 `members` 置 null（之后再 `add()` → NPE），故惰性挂载时若 `parent == null` 一律**新建**组、别复用旧对象。`Gizmo.destroy()` 只把 `parent` 置 null（**不置 `exists=false`**，那要 `kill()`）→ 判断「视觉是否已随场景销毁」看 `parent != null` 就够。
- **`Char.restoreFromBundle` 顺序 = 反序列化时已调 `restoreFromBundle` → 之后才 `attachTo`**：**别在 `attachTo` 里写字段默认值**（会覆盖读档值）；"空值兜底"放 `act()`。
