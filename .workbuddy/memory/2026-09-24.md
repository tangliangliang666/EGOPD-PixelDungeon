## 修 Bug：四条新考验全开时矮人国王二阶段卡死、不继续出怪

用户报「四个新考验全开的情况下，会导致第四个 boss 矮人国王二阶段卡死，不继续出怪」。
**根因是纯算术耦合，不是随机、不是时序**：

- `DwarfKing` 二阶段的「王座屏障」在原版里是一套**写死绝对量**的刻度：
  满值 = `HT`、每击杀一名二阶段仆从削减 `HT/12`（强化挑战 `HT/18`）、波次阈值 `200`/`100`（强化 `300`/`150`）。
  HT=300 时三者恰好咬合：`300 = 12×25`、`200 = 300×2/3`、`100 = 300×1/3`
  ⇒「第 4 次击杀放第二波、第 8 次放第三波、第 12 次打空进三阶段」。
  **唯一前提：HT 能被 12（强化 18）整除。**
- CHESED 给敌方生命上限 +25%（`Trials.CHESED_HP_MULT`）⇒ HT `300 → 375`，整除被破坏：
  ① 12 次击杀只削掉 `12×(375/12) = 372` ⇒ 屏障永远剩 3 点，三阶段永远进不去；
  ② 第 4 次击杀后屏障 `375 − 4×31 = 251 > 200` ⇒ **第二波永远不出**（用户看到的就是这条）。
- 而二阶段的国王 `isInvulnerable` 恒真（除 `KingDamager` 外免疫一切伤害）⇒ 玩家无解可打；
  `DKBarrior.act()` 的 `incShield()` 与 `Barrier.act()` 的衰减**正好互相抵消**（净 0）⇒ 也不会靠回合数自然磨掉
  ⇒ 真·死局。

**改法**（只改 `actors/mobs/DwarfKing.java`）：把两条刻度改成从 HT 现算，两条不变量对任意 HT 成立。
- `barrierKills()` = 强化 `18` / 常规 `12`（＝原写死值）
- `barrierChip()` = **`ceil(HT / kills)`**（向上取整 ⇒ kills 次击杀必定打空；原版是向下取整）
- `barrierThreshold(n)` = `HT × n / 3`（第二波 2/3、第三波 1/3）
- 四处波次阈值改走 `barrierThreshold( 2 | 1 )`（`summonsMade` 守卫原样保留）；`KingDamager.detach()` 与
  `Summoning` 被挡分支的削减量改走 `king.barrierChip()`（原来两处各带一遍 `isChallenged(...) ? 18 : 12`）。
- **HT = 300 / 450 时新算式与原字面量逐个相同（25 / 200 / 100 / 300 / 150）⇒ 不开本考验分毫不变**；
  不新增字段、不碰 `Random`。
- 落点 1 个文件；补丁脚本 `_chk/fix_dwarfking_chesed.py`（字节级 + 幂等 + 行尾增量断言，第二遍全 SKIP）。

## 副产物：两个工具学结论（都做了受控实验/证据）

- **`Edit` 工具会保留文件原有的行尾**：把上游 CRLF 文件 `Challenges.java` 复制成 `_chk/_crlf_probe.java`
  （111 CRLF / 0 裸 LF），用 `Edit` 改一行后仍是 **111 CRLF / 0 裸 LF** ⇒ 不会把整文件改写成 LF。
  所以「必须用字节级脚本」这条是针对**自己写的批改脚本**（Python 文本模式），不是针对 `Edit` 工具。
- **本仓自建文件可能是纯 LF**，不能一律按 CRLF 断言：`Trials.java`（390 行）、`GeburaGrace.java`（144）、
  `ChesedMend.java`（112）、`docs/*.md` 都是**纯 LF 且 untracked**；而上游跟踪文件（`Challenges.java` /
  `Rankings.java` / `HeroSelectScene.java` / `HeroClass.java` / `Brute.java`）都是 CRLF。
  ⇒ 批改脚本的行尾断言应写成「**无裸 LF + 行尾增量等于各条替换的行数差之和**」，
  而不是「CRLF 计数与改前相等」（插入行必然增加计数，这条断言本身是错的，本次就踩了）。

## 追加（同日晚二）：GEBURA 削弱「锁血那一击僵直一回合」+ 边界清单 + 出 v0.3.4

### 1. 需求与改法

用户：「触发 GEBURA 的锁血后，怪物等待一回合不行动，随后才正常行动（即刚触发锁血的那回合不会立刻行动）」。
原实现是「血停在 0、免疫伤害，但**照常出手**」⇒ 玩家把怪打进濒死反而立刻白吃一套攻击。

**落点 3 处（代码约 10 行，其余是解释性注释）**：

- `Mob.java` 字段区：新增第三个 GEBURA 瞬态标记 `public boolean geburaStagger = false;`（**不进存档**）。
- `Mob.java` 新方法：`public boolean consumeGeburaStagger()` —— **唯一消费点**，没标记返 false，有则**先清标记**再返 true。
- `Mob.java` `act()`：在 `paralysed` 分支**之后**（`chooseEnemy()`/`state.act()` **之前**）插
  `if (consumeGeburaStagger()) { spend( TICK ); return true; }`。
- `Trials.interceptLethalDamage`：发下豁免的同一处置 `mob.geburaStagger = true;`（顺序：门闩 → 僵直 → 挂 buff）。

**关键论证（写进了注释与 §8.12）**：
- **为什么是「下一次行动机会」而不是「扣掉这一刻的出手」**：闸门是在**别人的回合**里被调到的（英雄攻击结算 /
  `BruteRage` 战续结算），那一刻的「这一回合」并不属于它。
- **为什么不改成动时间轴**（如 `Actor.delayChar`）：会把 `GeburaGrace` 的**计时一起推后** ⇒ 无敌期间照样出手、
  总出手次数不变，**等于没削**。
- **僵直与豁免是两件事**：豁免可跨存档（存 `turns_left`/`source_class`），僵直是一次性瞬态、**刻意不进存档**
  （真读档时那一次僵直早已兑现，留着会平白多愣一回合）。豁免计时照常走 ⇒ 无敌期总出手 **−1** 即削弱本身。
- 形态刻意抄 `paralysed`/`FeintConfusion`（`spend(TICK); return true`），差别只有两点：一次性；**不动
  `enemySeen`**（它只是愣住，不是失去目标）。全程**不碰 `Random`**。

### 2. 边界：谁绕过 `Mob.act()`（**新增核验第 ⑥ 层**）

僵直消费点在 `Mob.act()` 里 ⇒ **自己写 `act()` 却不调 `super.act()` 的单位绕过它**。写了两个一次性扫描脚本

「唯一消费点」变成两处）。分类**人肉核对**过（阵营/EXP 大量来自父类实例块与运行时改写，正则推会推错）：

### 2. 为什么 `ICON_W/H` 必须是**恰好**包围盒（不是 ≤16 就行）

`WndTrials` 走 `icon.texture.uvRectBySize(x, y, ICON_W[i], ICON_H[i])`，
而 `Image.frame(RectF)` 里 **`width = frame.width() * texture.width`** ⇒ 这两个数**就是** `Image.width()/height()`。
写大了 ⇒ 图标自带透明边、在 16×16 槽内居中被推偏；写小了 ⇒ 直接被裁。
`WndTrials` 的居中公式 `(ICON_SLOT - icon.width())/2f` 再经 `PixelScene.align` 取整，
所以差 1px 就会变成可见的错位 —— 与 working memory 里「计数类图标与自然尺寸耦合」是同一类坑。

### 2. 关键设计（值得记）

- **「禁疗」靠收口，不靠打补丁**：唯一入口 `Char.heal(int)`，唯一判据 `HealBlock.blocks(ch)`
  （全仓 `HealBlock.blocks(` 调用点**恰好 1 个**，已钉成断言）。返回**实际回复量**，
  带浮字站点据此守卫 ⇒ 禁疗时不再弹假的 `+N`。
- **`onThrow` 的顺序就是语义**：`findChar` → 未命中 `super.onThrow`（落地可捡回）→ 白烟 →
  **`stopHiding()` 在 `HealBlock.apply` 之前**（若反了，`Mimic.add()` 的 NEGATIVE 自动暴露会
  **多播一次揭示特效**）→ 三 debuff；命中分支结尾**不调** `super.onThrow`（命中即消耗）。
- **白名单 9 条里 1 条是「设计选择」而非「它不是回血」**：`YogDzewa` 的两条阶段下限
  `Math.max(HP, HT - phaseStep()*phase)` / `Math.max(HP, finalPhaseFloor())` **刻意不受禁疗影响**
  （Boss 阶段刻度，HT 派生）。要改就改白名单检查那一处。
- 生成初始化 / 阶段血（`HP = HT`、`HT/2`、`Math.round(HT*pct)`）与下压钳制（`Math.min(HP, HT)`）
  **一律不收口** —— 否则 Boss 换阶段、分身生成、满血重算会全失效。探针 ③ 层把「它们仍在原地」
  逐条断言，防的正是**用力过猛**。

### 3. 踩坑（新，值得记）

- **放宽扫描正则后两类误报**：① `int postHP = HP + shielding();` 被当成 `HP = HP + x`
  ⇒ 需要 `(?<![\w])` 挡「标识符尾巴」；② `Math.max(1, HP-damage)`（CrystalGuardian 减伤）是
  **下压钳制不是抬血** ⇒ `Math.max` 只认**首参就是 `HP`** 的形式。
- **补丁 op 的旧块末行 `}` 可能是外层 `if` 的收尾**：一起替换掉就少一个右花括号（`Metabolism`），
  `javac` 只报 3 条「需要';'」，报错行离改动很远。⇒ **补丁脚本必须带括号收支审计**，
  别只看「脚本打印 OK」。
- **4 处替换在更深一级的行上少给了一级缩进**（`Healing` / `ThirstBloodBarrier` / `Metabolism` /
  `LifelongStew`）⇒ 手修 + **字节级 diff 全量核对 66 条 op 的增删行缩进**。
- **「浮字没用 `healed`」的 3 处（`TornPage` / `CrystalGuardian` / `Succubus`）是上游原有写法**
  （用 `_chk/_bak_heal_route/` 对照证实：改前就显示名义值）⇒ 只加 `>0` 守卫、
  **不改上游展示口径**（避免无谓 diff）。
- **javac 告警归因要「用原版同类对照编译」**：`WhiteSmokeParticle:63 [this-escape]`
  ≡ 原版 `SmokeParticle:49`（同款「构造函数里调 `color(...)`」）；
  `LloydTalisman:145 [rawtypes]/[unchecked]` ≡ 原版 `CharcoalResin:59`（`new Class[]{...}`）。
  这样才敢放行，而不是「看着像上游风格」。
