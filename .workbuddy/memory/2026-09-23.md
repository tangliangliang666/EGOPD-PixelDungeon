# 2026-09-23 封印之剑不可售 + 场景特效坐标速查

## 一、封印之剑系列「不可出售」

**症状**：封印之剑系列（四形态）能在商店被卖掉。

**根因（两层，缺一不可）**：
1. `Item.sellable()` 默认＝`!unique || stackable`，本系列**没标** `unique`（普通六阶武器，标了会顺带
   被禁掉锻造/附魔等）⇒ 默认可售；
2. `doUnequip()` 的「锁死在双手」**挡不住出售** —— 商店收购窗口是 `WndBag`，它的布局把
   `belongings.weapon`（主手）与 `belongings.secondWep`（副手）**一起** `placeItem`，
   所以剑挂在副手时就会出现在收购列表里、按六阶武器换钱。

**改动**：`items/weapon/melee/SealedSwordBase.java` 新增 `@Override public boolean sellable(){ return false; }`。
覆写**谓词**而不是加 `unique`（`Item` 注释已把这条约定写死）；基类一处覆盖四形态；
`Shopkeeper.canSell` 是全仓唯一消费点（实测 1 处）。

**核验**：新增 `_chk/verify_sealed_sellable.py`（35 断言 + 3 组反例 ALL PASS）；
`javap -c` 字节码实证新编译的 `sellable()` 是 `iconst_0; ireturn`，四个形态均无自己的覆写，
`Item` 默认与 `TearSwordBlessing`/`Admiration` 均未被误伤。

## 九、修：局内「考验 N」数字与挑战计数错位（用户实机发现）

**用户报的现象**：游戏内 `TRIAL_COUNT` 下方数字和挑战小图标下方的数字**没对齐**，问是不是尺寸配置不同导致的。
**结论：是的，就是尺寸差异。** 根因单一、传导链完整：

| | rect | `Image` 尺寸 |
|---|---|---|
| `CHAL_COUNT` | `uvRectBySize(160, 80, 7, 7)` | **7×7** |
| `TRIAL_COUNT`（修前） | `uvRectBySize(160, 88, 8, 8)` | **8×8** |

`MenuPane.layout()` 两段代码**逐行同构**，只有数值不同：
```java
challengeText.y = challengeIcon.y + challengeIcon.height();   // y+7
trialsText.y    = trialsIcon.y    + trialsIcon.height();      // y+8  ← 低 1px
trialsIcon.x = btnJournal.left() - 21 + (7 - trialsIcon.width())/2f - 0.1f;  // (7-8)/2=-0.5
```
- **纵向**：`+7` vs `+8` ⇒ 数字低 1px。
- **横向**：`(7-7)/2=0` vs `(7-8)/2=-0.5` ⇒ `left-21.1` vs `left-21.6`，`PixelScene.align`＝`round(pos*defaultZoom)/zoom`
  取整后变成 `left-21` vs `left-22` ⇒ 图标间距由设计的 7px 变 **8px**。

**先看图再改**：`analyze_icons_region.py` 逐行 ASCII 显示两枚字形**完全同形**（5×6，都落在格内 `+1,+1`），
差别只在**外框**（8×8 vs 7×7）。⇒ 收成 7×7 时字形占 `+1..+5 / +1..+6`，**一像素不切**。

**改动（一行）**：`Icons.java` 的 `case TRIAL_COUNT` → `uvRectBySize(160, 88, 7, 7)`，
并把「为什么必须同规格」写进 case 上方的行内注释 + 枚举处注释（8×8→7×7）。布局代码**一行没动**。
改后 `(7-7)/2=0` ⇒ 间距 7px、`y+7` ⇒ 数字同基线，与挑战完全一致。

## 十、实现第一条考验 HOKMA（智慧，序号 1）：三类「最终延迟」夹取

**需求（用户原话）**：「角色的**最终移动延迟不会小于 1**（最低为 1）；**怪物的最终移动延迟不会大于 1**
（最高为 1）；且角色的**最终攻击延迟不会小于 0.5**。以上调整均**优先于所有加速/减速的 buff 和各类效果**。」

| 对象 | 约束 | 等价写法 | 常量 |
|---|---|---|---|
| 英雄移动 | 最终延迟 **≥ 1** | `speed ≤ 1` | `HERO_MOVE_DELAY_MIN = 1f` |
| 敌方移动 | 最终延迟 **≤ 1** | `speed ≥ 1` | `ENEMY_MOVE_DELAY_MAX = 1f` |
| 英雄攻击 | 最终延迟 **≥ 0.5** | —— | `HERO_ATTACK_DELAY_MIN = 0.5f` |

两个岔口用户拍板：① 战士「手起刀落」那记免费击杀一击 → **压住、严格按规则**（夹到 0.5，天赋本身不改，
只改文案）；② 「怪物」→ **仅 `alignment == ENEMY`**（与 `AscensionChallenge.enemySpeedModifier` 同判据，
盟友与中立 NPC 不受影响）。

### 核心：单一终局（single terminal）+ `final`

移动延迟有几十处 `1/speed()` / `delay/speed()`，但**速度值只有一个出口 `Char.speed()`** ⇒ 只夹这一处就覆盖
**全部**站点（含将来新增的）。为了**子类无法绕过**，把 `speed()` 改 **`final`**、原实现改名 `speedRaw()`：

```java
public float speedRaw() { /* 原 speed() */ }                 // 子类覆写这里
public final float speed(){ return Trials.modifyMoveSpeed( this, speedRaw() ); }
```

**连锁改动：11 处 `speed()` 覆写改名 `speedRaw()`**（`super.speed()`→`super.speedRaw()`）——
这份「编译不过的清单」正好就是「**谁在偷偷改速度**」的完整答案：`Hero`（戒指/护甲/`Momentum`/挑战）、
`Mob`（接 `enemySpeedModifier`）、`CrystalGuardian`、`DM300`、`Ghost`、`RatKing`、`Thief`、
`PowerOfMany`、`ShadowClone`、`DriedRose`。它们**故意只覆写 `speedRaw()`**：自己的修正照旧生效，
出口仍只有一个，HOKMA 的夹子天然在它们之上。

### ⚠️ 只夹速度**不够**：`0 / speed` 恒为 0（本次最值钱的发现）

`Hero.move` 是 `float delay = 1;` → 天赋「夺命余势」（`GreaterHaste`）置 `0` → `spend(delay / speed())`。
**`0 / 任何数` 恒为 0** ⇒ 封顶速度**拦不住免费移动**。攻击延迟同理，它**根本不经过 `speed()`**。
⇒ 这两条必须**各自单独收口**：

```java
spend( Trials.modifyHeroMoveDelay( delay / speed() ) );      // Hero.move，最终值再夹一次
public final float attackDelay(){ return Trials.modifyHeroAttackDelay( attackDelayRaw() ); }
protected float attackDelayRaw(){ … if (buff(LethalMomentumTracker.class)!=null){ …detach(); return 0; } … }
```

**「内 / 外」就是要害**：LethalMomentum 的 `return 0` 必须留在 `attackDelayRaw()` **里面**，
才会被外面的 0.5 夹住；`attackDelay()` 不做 `final` 或把夹取挪进去，HOKMA 就会被天赋**击穿**。
（0.5 而非 1：攻击延迟基线恒为 1，0.5 是「最快每半回合一次」；移动延迟基线也是 1，所以下限取 1。）

### 特例：`CrystalGuardian` 的碎水晶追击绕过了出口

它自己写 `spend(1/super.speed())` —— **绕过 `speed()`**，但**不能改调 `speed()`**（`speed()` 会把它那记
「封闭空间 `/4`」**再乘一遍**）⇒ `spend( 1 / Trials.modifyMoveSpeed( this, super.speedRaw() ) )`。
⚠️ 通则：**改速度汇聚点时，除主出口外还要 grep 一遍自算延迟的站点**（`1/speed()`、`1 / …\.speed()`），
看有没有谁绕过了出口。

## 十一、调研：系统是否支持**负数**道具等级（为下一条考验铺路）

**结论：支持**，而且是**上游原生**（不是碰巧没崩）—— 数据层 / 存档 / UI 三层全通，上游有 **11 处显式**为负等级写的分支；
但**各品类的数值语义不统一**，分三档，动手前必须逐类确认。

### 三层支持度（全部实证）
- **运行时**：`Item.java:86` `private int level`；`:446-453` `upgrade()` 只 `level++`、`:463-468` `degrade()` 只 `level--` ⇒ **无下限夹取**。
- **`degrade(n)/upgrade(n)` 的 n ≤ 0 是空操作**（`for(i=0;i<n;i++)`）⇒ `Bones.java:229-233` 那种「归到某档」的 `degrade(level-3)` 天然安全。
- **存档**：`Item.java:646` 原样存；`:663-668` 还原 `if(level>0) upgrade(level); else if(level<0) degrade(-level);`。
- **显示**：`Item.java:489-492` `levelDisplay` = `Messages.format("%+d",…)` ⇒ 显示 `-3`（**不是 `+-3`**）；`ItemSlot.java:328-329` **专门有 `buffedLvl < 0` → `DEGRADED` 配色**。
- **临时降级**：`Degrade.java:57-61` 注释直接写「zero or negative levels are unaffected」。
- **本作自定机制也已考虑**：`GradeTestSword.java:16-18`、`BodyArtWeapon.java:273-275` 的字母制都先 `if (buffedLvl < 0) return super.levelDisplay(...)`。

### 三档语义（决定怎么用）
| 档 | 行为 | 品类 |
|---|---|---|
| A 显式支持 | 折价 / 换贴图 / 中性值 | 法杖·戒指·神器·**饰品**（`Trinket.java:48-60` 拿 **-1 当「未持有」哨兵**，全品类公式 `if (level<0) return 中性值` ⇒ **最完整的范式，可照抄**） |
| B 静默夹 0 | `Math.max(0, lvl)` ⇒ 压负数**没效果** | `Weapon.java:390`/`Armor.java:699` **STRReq**、`MissileWeapon.java:101-118` 伤害、`RingOfForce.java:116`、字形 `Affection/Thorns/Viscosity/Roach`、`WandOfRegrowth.java:232`、植物 `Earthroot/Sungrass` |
| C 负向传递 | 语义崩坏，甚至有**反向增益** | 近战 `min/max`、防具 `DRMax/DRMin`、法杖 `maxCharges`、戒指 `soloBonus` |

### C 档实测（真跑，tier2 短剑 / MagicMissile / 急速戒 / 板甲）
- **近战**：`min() = tier+lvl` ⇒ **-3 起负伤害**；**-10 时 `min(-8) > max(-15)` 区间反序**（`NormalIntRange` 仍能算，不抛）。
- **投掷**：写死 `Math.max(0,..)` ⇒ 恒 ≥0；但 `durabilityPerUse` 随等级**负指数**放大 ⇒ **-20 时除零得 `Infinity` ⇒ 一掷即碎**。
- **法杖**：`maxCharges = min(initialCharges()+lvl, 10)`。**`= -initialCharges()` 时上限 0 ⇒ 永远充不上电 = 死杖**（`curCharges < maxCharges` 恒假）；更负则**负充能**，UI 读数 `-1/-1`。（MagicMissile 初始 3 ⇒ -3 死杖、-4 负充能。）
- **戒指**：`soloBonus = level+1`，公式全是 `Math.pow(base, bonus)` ⇒ **效果反转**：急速戒**变慢**、元素戒**更痛**、力量戒**扣力量扣最大生命**。
- **防具**：`DRMax = tier*(2+lvl) + augmentFactor`，而 `if (lvl > max) return ((lvl-max)+1)/2` 这个「高等级软上限」分支**会被负等级误触发** ⇒ **DR 非单调**：板甲 `-2→0`、`-3→1`、`-10→**15**`（`DRMin=-10, DRMax=15`，掷出正数时**相当于一件好护甲**）。
  （已用实测反推出 `Augment.NONE.defenceFactor == 0`、`LeatherArmor` 实际是 **tier 2**（`super(2)`）—— 与公式逐格吻合。）

### 为什么不会崩（四道护城河，值得记住）
1. `Char.damage:1051-1055` `if (!isAlive() || dmg < 0) return;` ⇒ **负伤害不扣血、也绝不治疗**（不会打怪回血）。

## 十二、实现第二条考验 BINAH（理解，序号 2）：「生成时」等级规则（2026-09-23）

### 需求与一处关键补充
需求：**道具自然生成时不会带正等级；生成时掷出诅咒的道具，等级变为负数；任务 NPC 赠礼等级一律为 0**。
备注：**只影响「生成时」行为、不是全局行为**（诅咒道具生成时为 0 则仍为 0）。四区任务 NPC＝1 区幽灵、
2 区制杖人、3 区铁匠的锻造随机装备、4 区小恶魔。

**用户随后补充澄清了判定顺序**（我一开始就是按这个实现的，但值得记下来）：**先判「因诅咒反转」、
再判「正等级归零」**。理由：若先归零再反转，反转作用在已被清零的等级上 ⇒ **负等级永不出现**，
整条考验退化成「所有道具都是 +0」。

### 收口点：`Item.random()`（`final` 封口，与 HOKMA 同款）
「自然生成」全作唯一出口＝`Item.random()`（子类在这一个方法里先 `level(n)` 掷等级、再掷诅咒；
`Generator` 六个分支、宝箱/商店/房间道具、**雕像武器**、**装甲兽护甲**全经过它）。
`Item.random()` 改 `final` 转调 `Trials.modifyGeneratedItem(randomRaw())`，8 个子类
（`Armor`/`Artifact`/`Bomb`/`Gold`/`Ring`/`Wand`/`MissileWeapon`/`Weapon`）`public Item random()` → `protected Item randomRaw()`。
⇒ 编译期保证没有第二出口。**不在范围**：铁匠重铸（动玩家自己的道具）、升级卷轴/附魔、
开局自带装备、`Bones` 遗骸、`Statue` 生成后的 `weapon.cursed = false`。

### ⭐ 随机流不变量（本次最要紧）
改动**只读 `trueLevel()`/`cursed`、只写 `level(int)`**，全程不碰 `Random`

### 四处 NPC：为什么是「事后压平」而不是「跳过 upgrade」
四处赠礼都在 `Generator.random()` **之后**由 NPC 自己加等级（幽灵 +0~+3 武器与护甲各一次、
制杖人 +1 两根、铁匠 `level(rewardLevel)` 5 件、小恶魔 `upgrade(2)`），`modifyGeneratedItem` 拦不到，
故另加 `Trials.flattenQuestReward(Item)`（等级→0、**不动诅咒**）在各自加完等级之后调用。理由：
① `Ring.upgrade()` 内含 `Random.Int(3)`，**跳过 upgrade 会少消耗随机数、挪动随机流**，事后压平不碰 RNG；
② 制杖人那两根：`Wand.random()` 若掷诅咒 → BINAH 给负等级，NPC 随后 `cursed = false`
⇒ 只对「掷出的等级」归零会留下**无诅咒的负等级法杖**，事后压平一步到位。

## 13. BINAH 覆盖性排查：祭坛/墓室等「房间事后加工」漏网（待用户定方案）

**问题**：用户问「祭坛地形（击杀怪物后生成武器、必定诅咒）BINAH 能不能影响它」。

**定位**：祭坛 = `levels/rooms/special/SacrificeRoom.java`（`PEDESTAL` + `EMBERS` + `SacrificialFire`）。
「击杀怪物后生成」准确 —— `actors/blobs/SacrificialFire.sacrifice()`（148~214 行）在怪物/英雄死于火堆旁时
扣掉火的 volume，归零后第 203 行落 `prize`、第 205 行兜底重调 `SacrificeRoom.prize(Dungeon.level)`。

**结论：只覆盖「生成那一瞬间」，70% 被绕过。** 三个事实：
1. `SacrificeRoom.prize()` 第 87 行 `Generator.randomWeapon((Dungeon.depth/5)+1)` 走标准生成出口 ⇒
   **`Trials.modifyGeneratedItem()` 一定截得到**（出口值必定 ≤0）。
2. 但第 97~104 行是**生成之后**的房间脚本：`if (!prize.cursed) prize.upgrade();`（白送 +1）
   + `prize.cursed = prize.cursedKnown = true;`（人为补诅咒）。
   ⇒ **`prize.cursed` 在生成之后才置 true，规则②「生成时带诅咒」根本看不到它**；BINAH 也不改 `cursed` 字段，
   所以 `if (!prize.cursed)` 的分支判断与原版逐字相同。
3. 逐分支：生成未诅咒（70%）= BINAH 抹平到 0 → 房间 `upgrade()` → **最终 +1 诅咒，违反规则①**；
   生成已诅咒（30%）= BINAH 给 −n → `cursed` 已 true 跳过 upgrade → **最终 0/−1/−2，规则② 生效**。
   （等级 roll 与诅咒 roll 是独立两路：`Weapon.randomRaw()` 先 `Random.Int(4)`/`Int(5)` 定级，
   再 `Random.pushGenerator(Random.Long())` 另开一路 roll 30% 诅咒。）

**同型房间普查**（`levels/rooms/special/`）：
| 房间 | 生成物 | 诅咒 | 事后升级 | 现状 |
|---|---|---|---|---|
| `SacrificeRoom` 祭坛 | 武器 | 强制 true | 未诅咒时 +1 | 70% 绕过 |
| `CryptRoom` 墓室石棺 | 护甲 | 强制 true | 未诅咒时 +1 | 同上 |
| `PoolRoom`/`SentryRoom`/`TrapsRoom` | 武器/护甲/远程 | 强制 `false` | 33% 概率 +1 | 规则② 永不触发，但事后 +1 同样绕过规则① |
| `ShopRoom` | 武器/护甲/戒指/神器 | 强制 `false` | 显式 `level(0)` | 无问题 |

**修法坑（重要）**：补钩子必须在**事后 upgrade 之后**，且**不能复用现有两个钩子**：
- `flattenQuestReward` = 「非 0 一律归 0」，会把 30% 分支 BINAH 已算好的 −1/−2 也抹成 0 ⇒ **反而违反规则②**；
- 二次调 `modifyGeneratedItem` 会再取一次负（−1 → +1 → 0）⇒ **双重取负**。
⇒ 要么新增「只抹正等级」钩子（`if (trueLevel() > 0) level(0)`，保留负等级），要么新增「正等级取负」钩子。
钩子只写 `level(int)`、不碰 `Random` ⇒ **levelgen 随机流不变**（与 4 个 NPC 同理）。
**本案只做了调查，尚未改任何文件**，方案待用户拍板（目标等级：0 / 取负；范围：仅祭坛 / +墓室 / 含三个永不诅咒房间）。

## 15. 考验 CHESED（慈悲）+ GEBURA（严厉）—— 两条只作用于**敌方单位**的规则（当日续）

### 需求（用户原话要点）

- **GEBURA**：敌方单位**即将死亡时进入无敌，一定回合内不倒**；回合数 = **怪物可给予的经验数量**
  （5 经验 ⇒ 5 回合）；回合结束才死。⚠️ **判死/给无敌的时机要靠后**，别影响原版战续怪物（点名豺狼暴徒、矮人尸群）。
- 用户拍板：GEBURA **含 Boss**；无敌期间血量**停在 0（空血条）**；回合数取 **`Mob.EXP` 固有经验**。

### 结论：这是**第三类规则**（挡路型），不能套 HOKMA/BINAH 的收口
- HOKMA＝全局出口夹取；BINAH/CHESED 生命上限＝**事件型**（入场那一刻）；**GEBURA＝没有现成动作入口**，
  必须让原版流程**走到某一行**才判 ⇒ 钉在 `Char.damage` 的两行之间，靠「位置」生效。
- **CHESED +25%** 收口 = `Mob.onAdd()` 的 `firstAdded` 守卫里，**夹在 `AscensionChallenge.statModifier` 之后、
  `HP = round(HT*percent)` 之前**（怪物仍满血入场）；`restoreFromBundle` 置 `firstAdded=false` ⇒ **读档不二次放大**。
  ⚠️ 自带局限：HT 在**入场之后**才定的（`Bee.spawn`、Boss 换阶段、`Swarm` 分裂）拿不到 +25%。
- **CHESED 回血** 收口 = 常驻 buff `ChesedMend`，在 `Mob.onAdd()` 里**守卫之外**幂等重挂。
  ⚠️ **不能写进 `Mob.act()`**：63 个 `act()` 覆写里只有 44 个调 `super.act()`（`CrystalSpire`/`Masterpiece`/
  `MobSpawner`/`Sheep` 不调）⇒ 会整类漏掉。⚠️ **buff `type` 只能 POSITIVE/NEUTRAL**：
  `Mob.Sleeping` 把 NEGATIVE 当成「被打醒」⇒ 标 NEGATIVE 会让全图怪物入场就醒。
  回血量现算：`min(HT-HP, max(1, round(HT*CHESED_MEND_PERCENT)))`，口径全在 `Trials` 三个常量。
- **GEBURA** 收口 = `Char.damage`：`if (HP<0) HP=0;` → `GritTeethBuff.checkBypass` → **`Trials.interceptLethalDamage`**
  → `if (!isAlive()) die(src);`。「靠后」的收益：① 最晚可撤回点；② 子类 `die()` 还没跑 ⇒ `DM300` 不会在活着时
  `bossSlain()+unseal()+掉碎片`、矮人国王不会提前丢战利品（**子类 `die()` 全程只跑一次**，由 buff 计时结束时用
  **原始致死来源**调 `die(src)`）；③ **原版两种战续天然不过闸门、无需白名单**：`Brute` 覆写 `isAlive()`（护盾没耗尽
  就算活着 ⇒ 闸门问不到它）、`Ghoul` 在 `super.die()` 前 return ⇒ 用 `Mob.deathIsDeferred()` 显式让路
  （判据与 `die()` 分支**同源**＝`GhoulLifeLink.searchForHost`，纯查询不碰 Random）。
- **不倒+无敌都复用原版**：覆写 `Mob.isAlive()` 返 `super.isAlive() || geburaGrace`（血停 0 仍不倒、
  `isActive()` 也为真 ⇒ **仍会照常行动**）；覆写 `Mob.isInvulnerable(Class)` ⇒ 原版无敌分支吃伤害 + 弹
  `actors.char.invulnerable`（键已存在）、盟友自动不打它。
  ⚠️ **`isAlive()` 里不能现查 `buff(...)`**（原版注明它在**绘制期**被调用）⇒ 缓存进 `Mob.geburaGrace` 布尔字段，

### ⚠️ GEBURA 的**作用范围**（本次划界，用户可能追问）
**只管「被打死」（伤害致死），不管「被机制直接终结」** —— 闸门只钉在 `Char.damage` 一处，
所以一切**绕过伤害、代码直接调 `die()`** 的终结照原版立即生效。全库分类（`grep -rn "\.die(" core/src --include=*.java`）：
- **战续结束**：`Brute`/`ArmoredBrute` 的 `target.die(null)`（`BruteRage` 到期）—— 用户点名要保护的豺狼暴徒，
  **绝不能接**（接了＝狂暴结束再白送 N 回合）。
- **处决/必杀**：`Char.attack` 两处 `enemy.HP = 0; → enemy.die(this)`（`Preparation.canKO` 潜行处决、
  `Talent.COMBINED_LETHALITY`）、`DeathMark`、`NeverForget` —— 「必杀」的语义本就该压过「濒死无敌」。
- **脚本/剧情/机制**：`Chasm` 落坑、`SmokeBomb`、`DwarfKing` 阶段清场、`Necromancer`/`SpectralNecromancer`
  献祭、`RotHeart`、`Ghoul` 的 `GhoulLifeLink` 超时、`Berserk`/`GritTeethBuff`、剧情演出。
判据一句话：**没有「这一击是否致命」这个语义的终结，都不该硬接**。将来若要纳入某处，就在该站点 `die()` 之前
插同一个 `Trials.interceptLethalDamage(ch, src)`（钩子与来源无关，探针 §③ 已证「任何 src 类别都免疫」），
但**先确认它不属于「战续 / 剧情」两类**。已写进 `docs/features.md` §8.5.1（含表格）与 `Trials.java` 的 GEBURA 注释。
