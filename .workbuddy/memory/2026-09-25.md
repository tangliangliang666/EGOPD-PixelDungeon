1. **不是裸剪 16×16**，而是按 `alpha>0` 包围盒裁 —— 实测包围盒尺寸
   `13×16 / 15×13 / 15×14 / 15×14 / 13×16 / 16×15 / 15×15 / 15×14 / 15×15 / 15×16`，
   与 `Trials.ICON_W/ICON_H` **逐项相等**。游戏里 `uvRectBySize(i*16, 0, W, H)`
   （=`uvRect(l,t,l+w,t+h)`，像素矩形）走的也是同一口径 ⇒ 预览与实装一致。
2. **10 个包围盒全部锚在各自 16×16 格的左上角 (0,0)**，空白留在右/下（最多 3px）。
   ⇒ 只有「从格子左上角起裁」才对；若改成「把裸 16×16 居中」，会按 `(16−W)/2`、`(16−H)/2`

   **用户看到的「偏左」正是这个**。已出并排对照图 `_chk/_icon_center_compare.png`（左对右错）。
3. **三行 `alpha>0` 包围盒逐格完全一致**（`_chk/verify_tree_rows_bbox.py`：不一致 0/10）
   ⇒ **一套 `ICON_W/H` 裁三行是安全的**，切状态行不用改常量，只改 `frame()` 的 `y` 加 `row*ICON_FRAME`。
   （`alpha≥128` 的实体盒在 KETER/BINAH 上三行不同，那只是 row1 均匀灰度导致的阈值漂移，与裁片无关。）

**实体居中实测**：`实体相对框中心` = (0,0) 对 9/10；仅 TIPHERETH 偏 **(-0.5, 0)**（其 halo 16 宽触到格子两缘）。
⇒ 用户决定 **保持现状、不动 `tree.png`**。

**窗口宽度定案**：用户选「**使树可以按照比例缩小**」⇒ 采纳整体等比缩放方案，**窗口内容宽维持 140**。

| 量 | 定值 |
|---|---|
| 缩放 `s` | 0.70（不用 0.74：0.74 恰好贴边，0.70 才左右各留 ~4px） |
| `a` / `h` | 70.0 / 60.62 |
| 图标显示 | **整数** `round(原生×0.70)` = 9~11px（整数尺寸 + NEAREST ⇒ 单图标自身不出现像素翻倍不匀） |
| 树外包 | 132.2 × 291.0（`宽 = a·√3 + 图标外包`、`高 = 4a + 图标外包`） |

| 线 | 1px，`#000`@35%，`TRIM = 0.28a ≈ 19.6` |

**容量判据（记住这个式子）**：`树宽 = a·√3 + 图标外包 ≤ 内容宽`；140 下 `a ≤ 71.6`。

## 实装：生命之树考验界面落地（同日后续轮次，用户明确授权实现）

**用户指令**：① 要缩放图标时**不缩放图标本身**，只改显示尺寸（**不许 LANCZOS/重采样**）；

**核心手法（记住这条）**
- `Image.frame(uvRectBySize(...))` 会把 `width/height` 设成**原生像素数**；
  要显示更小**不能改 frame、也不能重采样纹理**，只能 `icon.scale.set(dw/W, dh/H)`
  —— `Visual.scale` 是 `PointF`，**支持非等比**；GPU 按 scale 采样原生像素。
- ⇒ 缩放＝**纯显示层**，`tree.png` 一个像素不动；13→9 的下采样由 GPU NEAREST 在绘制时完成。
- 缩放后取**整数**`round(原生×0.70)` = 9~11px（整数尺寸 + NEAREST ⇒ 单图标内不出现像素翻倍不匀）。

## 20:05 考验详情窗「开启该考验」点不动 —— 根因是**构造顺序**

**用户报**：开关点击后无反应。

**根因（读源码查实，不是猜）**：`Button` 的 `PointerArea` 在**构造时**（`Component()` → `createChildren()`）
就注册进全局 `PointerEvent` 监听表；那张表是 `new Signal<>(true)`（**stackMode**：`add()` 走 `addFirst`、
`dispatch()` 从队首遍历、**首个返回 `true` 就 return**）⇒ **后注册者优先、第一个命中的吞掉其余**。
`Window` 构造会加一个**覆盖全屏**的 blocker（点窗外即关窗），且它照样拦截
（`Gizmo.isActive()` 只看 `active && parent.isActive()`、**不看 `visible`**，blocker 正是 `visible=false`）。
原实装是「先 `new CheckBox(...)` 再 `new WndTrialInfo(...)`」⇒ 开关比该 blocker **早注册**，每次点击都被
blocker 抢先吃掉；树上质点能点，恰恰因为它在 `super()` 之后构造。

**修法**：开关改由 `WndTrialInfo` **自己**在 `super(...)` 之后构造，调用方只传
`toggleLabel / checked / toggleActive / ToggleListener`；`WndTrials` 里连 `CheckBox` 这个词都不许有。

**另一件**：`tree.png` 的 TIPHERETH 帧右侧那道极薄不透明像素已被用户擦除 ⇒ `Trials.ICON_W[5]` 16 → 15
（实测三行均 15×15），最大图标显示宽 22 → 21、树外包宽 104.27 → 103.27、左右余量 7.86 → 8.36。
顺带修了 `verify_tree_trials_icons.py` 一条**过期判据**（整图高按「单行 16」写死，而 tree.png 早已 3 行 48 高）
⇒ 改成 `ICON_ROWS * ICON_FRAME`。**陈旧判据会永久报红、把真回归埋掉，见到就修。**

**核验（全绿）**：javac EXIT=0（仅 2 条既有 `this-escape`）、`check_utf8_all.py` 1462 文件、

## 续：修 Bug —— GEBURA 濒死无敌「延后死亡」⇒ 幸运附魔 / 财富戒指的**额外掉落判定**落空

**用户口径**：只要怪物触发 GEBURA 无敌，幸运附魔与财富戒指的额外掉落都不生效；
补充「财富戒指**增加原本基础掉率**的可能生效，但**额外掉落生成**不生效」。

**根因**：`Mob.rollToDropLoot()` 三段＝基础掉落 / 财富额外 / 幸运额外，**后两段读的是「致死那一击那一刻」的状态**；
vanilla 靠「攻击→伤害→die **同一调用栈**」才读得到，而 GEBURA 把真正倒下推迟了 `EXP` 个回合：
- **`LuckProc` 必然已不在**（它只活到下一个 buff tick，`act()` 第一句就是 `detach()`）⇒ **主因**；
  连带 `Mob.die` 传给 `RingMasterLoot` 的 `luckyProc` 实参恒为 false（素材的「幸运再判一次」也失效）；
- **财富等级是英雄侧凭据**，延后期间同样可能与判定时刻不一致（复活/卸下）—— 不像 LuckProc 那样必然消失，
  与用户「可能是生效的」吻合，但**判定口径本身错**，一并收口。

**一句话原则**：**掉落的额外判定按「致死那一击那一刻」的凭据算，物品落地仍在真正死亡那一刻。**

**修法（不提前结算）**：闸门在 `geburaUsed` 之后、`Buff.affect(GeburaGrace)` 之前抄两份凭据到 Mob
（`geburaLuckyProc` 抄**实例**⇒掉落强度一并留存；`geburaWealthBonus` 抄等级读数），
死亡时一律 **live 优先、取不到才回落**（未开启本考验时逐字不变）。三个要点：
① 等级必须**当参数传进** `tryForBonusDrop` —— 它内部会自查 `getBuffedBonus`，只放宽外层守卫等于白抄
⇒ 新增三参重载（二参重载转调，原调用方一字未改）；
② 已 `detach` 的 `LuckProc` 仍可消费（`Buff.detach()` 是 `target.remove(this)`，
`Char.remove(Buff)` **不置空 `buff.target`** ⇒ 二次 detach 幂等）；
③ 两份留存**刻意不进存档**（豁免用掉的结局一定是真死，死者不进存档）。

**落点**：`Mob.java`（2 字段 + `die()` 的 luckyProc 布尔 + `rollToDropLoot()` 两段）、
`Trials.java`（2 行抄写，**不碰 Random**）、`RingOfWealth.java`（三参重载）。行尾：前两个 LF、后者 CRLF。

**核验（全绿）**：`verify_gebura_drop.py` **37 条断言 + 36 条反例（0 条抓不到错）**；
新行为探针 `GeburaDropProbe.java` **26 条断言全过**（① LuckProc 跑一次 act() 即自行摘掉 ② 抄下的就是那一击的实例
③ 计时走完后 live 没了而留存仍在 ④ 已 detach 的实例二次 detach 幂等且能产出掉落 ⑤ 关掉 GEBURA 两字段恒为初值
⑥ 同 seed 200 个随机数逐位相同 ⑦ 财富等级抄的是致死那一刻读数、live 归 0 后仍可判）；
`verify_chesed_gebura.py` 既有 155 条口径未被破坏；javac EXIT=0（仅既有 rawtypes 告警）。

**遗留事实**：财富那条属「判定口径收口」的加固（`LuckProc` 是可直接复现的主因）；

## 27 层测试层草叶细节区段更正：第一区 → 第二区（监狱）

用户报「27 层的草地特征贴图（`terrain_features.png`）被错配成 1 区，改为 2 区」。
- **根因**：09-19 把 `LobTestLevel.featuresStage()` 写成 `(GEN_DEPTH - 1) / 5`（= 0，第一区下水道）。
  但 `GEN_DEPTH = 4` 只是**生成期借用的布局深度**（房间池/水/BGM/配色），与本层 `tilesTex()` 的
  草皮材质**无关**——`tiles_lob.png` 槽 250 与 `tiles_prison.png` 槽 250 **逐像素相同**

  与 `GEN_DEPTH` 解耦；判据改写为「报**草皮材质**所属区，不是**布局**借用深度」。
