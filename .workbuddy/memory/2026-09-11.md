## 修复「溶解之爱移动不转身 / 停止不回待机」+ 爱慕快捷栏赠予（2026-09-11 追加）

**（1）移动不转身 —— 根因在引擎的顶点刷新时机**
- 链路：`Char.moveSprite(from,to)` → `CharSprite.move()` = **先 `turnTo(from,to)`（只改 `flipHorizontal`）再 `play(run)`**。
  而 `flipHorizontal` 只在 `Image.frame()` 内部调用的 `Image.updateFrame()` 里被写进顶点数组。
- `MovieClip.updateAnimation()` **只在帧索引变化时**（`curFrame != lastFrame`）才调用 `frame()`；
  `MovieClip.play()` 在 `curAnim == anim && (looped || !finished)` 时**直接早退**。
- 于是"移动动画只有一帧 + 循环"时：帧索引恒为 0 → `frame()` 永不调用 → 翻转永不写进顶点 →
  表现就是**移动时贴图朝向卡住不转**（旧配置的"老 bug"，不是 turnTo 的问题）。
- 修法（`MeltingLoveSprite`）：① 移动帧写**两帧同姿势** `run.frames(frames, b+F_MOVE, b+F_MOVE)`
  （索引 0↔1 切换 → 周期性触发 `frame()`）；② 覆写 `move(from,to)`：`super` 之后若 `curAnim == run`
  就 `play(run, true)` 强制重播，立即刷新顶点；③ `loveanger` 的 run 同样写两帧。
- **通用教训**：**SPD 里任何"单帧循环"动画都不会触发 `frame()`**，因此 `flipHorizontal` / 换贴图尺寸
  之类的顶点级改动都不会生效；需要 ≥2 帧，或显式 `play(anim, true)` 强制刷新。

**（2）停止移动后不回待机 —— 怪物侧没有收尾逻辑**
- 全仓排查：`sprite.idle()` 的调用点里**没有** `Mob` / `Char` / `Ally` / `DirectableAlly`——怪物侧
  没有 run→idle 收尾（英雄侧才有：`Hero.ready()` 里 `if (sprite.looping()) sprite.idle()`；
  `CharSprite.onComplete(Animation)` 也只处理 attack/operate）。故移动结束后 `curAnim` 停在 run。
- 修法：覆写 `onComplete(Tweener)`，`tweener == motion` 且 `ch.isAlive()` 时 `idle()`。
  **必须在 `super.onComplete(tweener)` 之前调用**——super 里的 `notifyAll()` 会唤醒行为线程，
  可能立刻发起下一次 `move()`，放在 super 之后就会把新一轮 run 覆盖掉。
  死亡时（`!isAlive()`）不 idle，避免打断 die 动画、丢掉 `MobSprite` 的淡出（AlphaTweener）回调。

**（3）爱慕「赠予」进快捷栏**
- 覆写 `Admiration.defaultAction()`：`isEquipped(hero)` 时返回 `AC_GIFT`，否则 `super.defaultAction()`
  （父类为 null → 点按无反应，与改动前一致）。
- 依据：`Item.execute(Hero)` = `String a = defaultAction(); if (a != null) execute(hero, a);`，
  而 `defaultAction()` 注释明确"can be overridden if default action is variable"。
  单参 `execute(Dungeon.hero)` 的调用点：`ui/QuickSlotButton.java:102`、`ui/Toolbar.java:180/463`、
  `ui/InventoryPane.java:569`、`windows/WndQuickBag.java:107`——即快捷栏/工具栏/背包双击都会走赠予。
- 快捷栏点按还有前置 `Dungeon.hero.belongings.contains(item)`（装备中即包含），故装备状态下必定可触发。

### 关键实现点（详见 `docs/features.md`「泪剑」节 + `AGENTS.md` §8）

- **挂载**：视觉是 `Group`（非 `Visual`），**不能**走 `GameScene.effect()` → 用
  `target.sprite.parent.add(visual)`（= `GameScene.mobs`，与 `MasterpieceShow` 同范式）。

  取中点既保证 n=1 时 θ=90°（正头顶），又保证任何 n 都不落在 0°/180° 水平端（否则与腿脚重叠）。

- **拖尾**：`CharSprite.move()` 用 `PosTweener` 平滑滑动，故按 `TRAIL_INTERVAL=0.05s` 采样，

- **buff 生命周期**：`fx(true)`（`attachTo` / `Char.updateSpriteState()`）建视觉，`act()` 每回合

## 泪剑第四轮：修复「协同攻击不触发」+ 落实协同法术伤害

**根因 = 一行缺失的语句**：`TearSwordVisual.update()` 里 `strike()` 起手把 `strikeTimer` 置 0，
但**全类没有任何地方执行 `strikeTimer += dt`**（`time += dt`、`trailTimer += dt` 都在，唯独漏它）。双重静默失败：
① 计时器恒 0 ⇒ `strikeAmount(0 − i·0.035)` 对每柄剑都返回 `0f` ⇒ `amt > 0f` 永不成立 ⇒ **剑一动不动**；
② `striking` 永远为 true ⇒ 突刺状态**永远退不出去**。不抛异常、不打日志 ⇒ 表现为"特效静默失效"。
修复：`if (strikeTimer >= 0f) { strikeTimer += dt; if (strikeTimer > strikeTotal(n)) strikeTimer = -1f; }`

**协同伤害**：
- 新增 `TearSword.DAMAGE_PER_SWORD = 1`，伤害 = 层数 × 本值（数值集中在一个常量，留后续调整空间）。
- `strikeAt()` 触发动画后追加 `target.damage(dmg, b)`（**以 buff 实例为来源**，同 `Bleeding`/`Burning`/`Corrosion` 写法）。
  `Char.damage` 不结算护甲（护甲在 `Char.attack` 的 `defenseRoll` 里）⇒ 直接调 `damage()` 天然「无视护甲」，贴合法术伤害定位。
- **法术图标**：在 `Char.damage` 图标分支加 `if (src instanceof TearSword) icon = FloatingText.MAGIC_DMG;`。
  **刻意没有**登记进 `AntiMagic.RESISTS`——该集合还会被 `MagicImmune.attachTo()` 拿去按类清除 buff、
  被 `ChampionEnemy.AntiMagic` 拿去完全免疫，对纯特效 buff 来说连带效应太重（同处已有 `DimDusk.FlameStrike` 先例可循）。
- **调用点从 `attack()` 前移到后**：泪剑伤害若先把目标打死，`attack()` 会在尸体上白跑一遍（命中判定/附魔/Tracker 都在里面）。
  放到之后则先正常结算挥击、泪剑伤害作为"追加"。副作用：这一击本身已击杀时，泪剑伤害被 `Char.damage` 的
  `!isAlive()` 兜底跳过（动画照播）。目标坐标取样仍然有效——死亡只是原地播动画，贴图 x/y 不变。
- 已知小瑕疵：两段伤害同帧结算 ⇒ 两个伤害浮字叠在同一位置；要错开需把伤害延迟到突刺命中那刻、从视觉层回调游戏逻辑
  （`MissileSprite` 的 callback 是先例），本轮刻意不做，保持"伤害在挥击结算处一次算清"。

- **击杀归因**：泪剑的伤害来源是 buff 实例，而 `Mob.die()` 有一段「是否算英雄击杀」的白名单
  （`cause == Dungeon.hero || cause instanceof Weapon || ... || Electricity`），命中才结算指令击杀计数、
  环指大师素材掉落、小小银河/笑靥、BOSS 判定、神谕庇佑、致命势能/迅捷 ⇒ 已加 `|| cause instanceof TearSword`
  （同 `DimDusk.MagicStrike`/`FlameStrike` 的先例）。EXP 与杀敌统计不受影响（在 `Mob.destroy()` 结算，无 cause 参数）。
  （对照：`Bleeding` 是"非英雄直接伤害"，没进白名单，只在环指大师职业下补发掉落。）

改动：`TearSwordVisual`（补 1 行）、`TearSword`（常量 + 伤害 + javadoc）、`Hero`（钩子移位）、`Char`（图标分支 + import）、
`Mob`（英雄击杀白名单 + import）、zh/en `desc`。括号配平通过（6 个文件）；**未代编译**（惯例），请跑 `build-desktop.bat`。

### 追加（同日）：泪剑伤害登记进 AntiMagic.RESISTS
- 需求：泪剑伤害要被「魔法免疫」抵挡。
- **机制定位**：`Char.damage` 里 `if (isImmune(srcClass)) { damage = 0; }`；`MagicImmune`（反魔法卷轴）与
  `ChampionEnemy.AntiMagic`（绿色「魔法免疫」精英）都是 `immunities.addAll(AntiMagic.RESISTS)`
  ⇒ **登记 RESISTS 就是唯一且充分的开关**。（本版本 `Char.isInvulnerable` 只管 SpectatorFreeze/Invulnerability，
  **不看 MagicImmune**——别找错地方。`Char.glyphLevel` 对非英雄返 `-1` ⇒ `drRoll` 返 0，普通怪不会被雕文减伤。）
- 改动：`AntiMagic.RESISTS.add( TearSword.class )`（+import）；删掉 `Char.java` 里冗余的 `instanceof TearSword`
  法术图标特判与 import（`RESISTS.contains(src.getClass())` 已覆盖，且是**精确类相等**）；`TearSword` javadoc 改写。
- 副作用（已接受）：`MagicImmune.attachTo` 会按类驱散持有者身上的 Buff ⇒ 英雄用反魔法卷轴会掉泪剑；
  免疫期间 `Buff.affect` 失败。**新发现**：`Buff.append` 把 `attachTo` 的 false 丢掉、照旧返回实例 ⇒
  `addStacks`/`setStacks` 拿到的是 `target == null` 的「幽灵」对象（`ensureVisual` 的 `target == null` 分支由此
  第一次变成可达路径，已确认 `freeVisual` 有 null 兜底、不会 NPE），已补 `b.target == null` 早退。
- **未代编译**（惯例），请跑 `build-desktop.bat`。验证点：绿色「魔法免疫」精英 / 反魔法卷轴状态下泪剑伤害为 0。

### 追加（同日·修正）：泪剑不再被自己的魔法免疫驱散 + 协同突刺剑尖转向目标
- 需求①：消除上一节的副作用 —— 泪剑只保留「伤害被魔法免疫抵挡」，buff 本身不被驱散。
  **做法**：伤害来源从 `TearSword` 这个 Buff 实例换成**非 Buff 的空标记类 `TearSword.MagicStrike`**
  （`DimDusk.MagicStrike` 范式）；`AntiMagic.RESISTS` 改登记 `TearSword.MagicStrike.class`；
  `Mob.die` 白名单同步改判 `cause instanceof TearSword.MagicStrike`。
  `RESISTS` 的三处消费点里**只有 `MagicImmune.attachTo()` 关心「是不是 Buff」**（`isAssignableFrom` 类匹配、
  遍历 `target.buffs()`），标记类不是 Buff ⇒ 匹配失败 ⇒ 免伤保留、泪剑留下，免疫期间也能正常叠层。
  行为等价性已核查：`src` 前后都不是 `Char`/`Hero` ⇒ `Char.damage` 其余分支（保护光环减伤、寂静代价、
  `isInvulnerable`）全部不变。
- 需求②：协同突刺要有「戳刺感」—— 突刺时**剑尖转向怪物**，收剑回位过程中同步转回原位。
  **角度公式**：`angle = toDegrees(atan2(gy−cy, gx−cx)) − (朝左 ? 135° : 45°)`（贴图剑尖相对 origin (9,9)、
  未旋转方向角 45°；朝左 `scale.x = −1` 使基准角变成 135°）。`(gx,gy)` 取**该剑自己的落点**（含
  `STRIKE_REACH`/`STRIKE_SPREAD`）⇒ 三柄剑朝向略有分叉，与各自轨迹一致。
  **分段**：新增 `strikeRotate()` —— 冲刺段前 `STRIKE_TURN_PART = 0.4`（即 0.04s）就转到位、之后纯位移；
  收回段与位移共用同一条 smoothstep 归零曲线 ⇒ 边收边转回原位。角度插值经 `angleDelta()`
  归一化到 (−180, 180]，避免绕远路。
  **验算**：用 `glwrap/Matrix.rotate` 的真实矩阵（列主序 `p' = (x·cos − y·sin, x·sin + y·cos)`，
  正角=顺时针）对 8 方向 × 2 镜像共 12 组合计算剑尖最终指向，**全部零误差**；θ=0/180 代回即得
  −45°/45°，与原有原位角自洽。时间曲线实测：t=0.04 时转向进度 1.0、位置进度才 0.352；收回段两列完全相等。
- 顺带：`addStacks`/`setStacks` 的 `b.target == null` 兜底**保留**（泪剑已不再被自己的免疫拦下，
  但对其它 `attachTo` 失败路径仍是零成本保险，且 `Char.damage` 侧不变）。
- 文案：zh/en `desc` 补「突刺时剑尖转向目标」「可被魔法免疫抵挡，但不会因此驱散泪剑」。
- 改动文件：`TearSword`（+`MagicStrike` 内部类、伤害来源、javadoc）、`AntiMagic`（登记类替换）、
  `Mob`（白名单）、`TearSwordVisual`（`STRIKE_TURN_PART`/`strikeRotate`/`angleDelta` + 角度计算 + 类注释）、
  zh/en `desc`。括号配平 + 角度数值验算通过；**未代编译**（惯例），请跑 `build-desktop.bat`。
- 验证点：① 吃反魔法卷轴后泪剑**仍在环绕**，协同伤害显示 0（带法术图标）；② 近战**斜角方向**的怪时
  能明显看到剑尖先转向目标再戳出，收回时转回原位（正左/正右本来就已对准，差异小属正常）。

## 前二老板皮肤「泪锋之剑」：选角界面开关 + 游戏内恒定第 8 行外观
- 需求：用户把新皮肤画在 `valencina.png` **第 8 行（索引 7，原为空白预留行）**，要求在角色选择界面加开关「泪锋之剑」，开启后正式游戏中无论穿什么护甲都显示该行皮肤。
- 实现（4 个消费点统一走 `HeroSprite.skinTier(cls, armorTier)`）：
  - `SPDSettings`：新增 `KEY_VALENCINA_SKIN="valencina_skin"` + `valencinaSkin()/valencinaSkin(boolean)`（全局布尔，默认 false；进游戏后读档同样生效）。
  - `HeroSprite`：`public static final int VALENCINA_SKIN_TIER = 7` + `public static int skinTier(HeroClass,int)`；`updateArmor()` 拆为 `updateArmor(boolean allowSkin)`（`disguise()` 传 false，伪装成其它职业时不套皮肤）；`avatar(Hero)` 走 skinTier。
  - `HeroSelectScene`：新增 `CheckBox skinCheck`（文案键 `scenes.heroselectscene.valencina_skin` = 泪锋之剑 / Blade of Tears），**仅选中 VALENCINA 时显示**；横屏居中于 `heroDesc` 与 `startBtn` 之间、竖屏放 `startBtn` 上方；`updateFade()` 同步 alpha/active；勾选后 `refreshHeroIcons()` 把 HeroBtn 图标切到皮肤行首帧。
  - `StartScene.saveSlotIcon` 调用处、`WndGameInProgress`/`WndRanking` 的头像均改用 `skinTier`，保持处处一致。
- **关键机制**：非 RING_MASTER 职业的 `HeroSprite.tiers()` 复用 ROGUE 的 film（`new TextureFilm(texture, 256, 15)` ⇒ cols=1、rows=128/15=8），索引 0..7 均有效且 UV 按 256×128 归一化。行 0-5=护甲 tier、行 6=ClassArmor(tier 6) 兼选角立绘、**行 7=皮肤**。故皮肤行**无需改贴图高度**（仍 256×128）即可 `film.get(7)`；代价是自定义职业贴图必须保持 256×128，否则 UV 错位。
